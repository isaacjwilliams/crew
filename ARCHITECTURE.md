# Architecture

This document is for anyone changing the crew, human or Claude Code. `SETUP.md` covers installing and using it. This file explains how the pieces fit together, the contracts between them, and the invariants that changes must preserve.

## What the system is

Eight Claude Code agents run on one machine at a time (principle 8):

- **lead**: the only agent you talk to, for every project, from a terminal or from Claude Mobile. It turns requests into briefs, dispatches work, routes PR feedback, and reports status.
- **implementer**: one background session per task, each in its own git worktree and branch. It opens a PR and addresses review rounds.
- **casual-observer**: a read-only readability review, spawned by workers before a PR (or used ad hoc).
- **brief-reviewer**: a read-only review of whether a finished brief's objective and gates will get the user's problem solved, spawned by the lead before the user approves it. It never proposes a design.
- **reviewer**: a read-only, adversarial review of a worker's open PR, spawned by the `pr-review` skill the worker runs after opening it. When Codex reviews too (`CODEX_REVIEW`), a fresh reviewer answers Codex's findings in each rebuttal round.
- **gardener**: runs on a schedule and turns merged commits into refactor *proposals*, never code. A proposal is any idea worth keeping that isn't a task yet; the user, a lead or a worker can write one too.
- **misses**: runs with the gardener. It sorts the user's review comments on merged PRs that automated review had been through, and proposes a fix at their source: the repo's AGENTS.md, a lint rule, the user's taste file or crew's review rubric.
- **goal-lead**: one background session per goal the user starts. It does the lead's intake for every item of the goal, without the user.

They coordinate through the **ledger**: Markdown files under `projects/` in the crew home, a clone of the person's private repo, driven by a CLI, `crew`, and pushed to that repo as they change. The crew's code is a public repo; each person's private repo is a copy of it with the ledger added.

## Design principles

These are invariants. Breaking one changes the design, not just the implementation. A change that weakens one needs the user's say first: raise it before writing the code.

1. **Nothing coordination-related touches the shared repo.**
   - No labels, comments other than the ones below, committed config, or files in the working tree. The repo belongs to other people too.
   - The only repo-side footprints are:
     - task branches pushed under `BRANCH_PREFIX`, after every commit;
     - the PRs workers open;
     - optional one-line replies to the user's own review comments: in the thread for an inline comment, otherwise as a PR comment that quotes the one it answers;
     - one comment per pass of automated review summing it up (`crew review-summary`), which a worker edits rather than posting a second for the same pass;
     - one comment for each commit CI went red on after the worker handed its PR over, saying why and what it did (`crew ci-summary`), edited rather than posted twice for the same commit;
     - 👀 and 🚀 reactions to the user's own review comments (`crew react`): picked up, and being changed;
     - two lines in `.git/info/exclude`, which is local to the clone.
2. **The ledger is the single source of truth, it's plain text, and it's pushed to the person's private remote.**
   - Every change is committed at once and pushed in the background, normally within seconds, so another machine can take over with what this one knew. A push that fails is retried by the next commit, and by every `crew tick`.
   - Agents never rely on their conversation for state. The lead is effectively stateless: every session starts by reading the ledger.
   - That holds for a long conversation too. The lead opens a draft task once the goal is agreed and writes each decision into it as it's made; the lead and workers reread the task file after a compaction or a resume. Compaction and fresh sessions lose nothing that matters, so no conversation has to live forever.
   - Task files hold the brief, the decisions, the review rounds, a log, and the worker's identifiers.
3. **Work has identity; sessions are disposable.**
   - A task file records how to reach its worker (`worker_session`, `worker_job`, `worker_name`) and where its work lives (`worktree`, `branch`, `pr`).
   - Routing feedback is a lookup, not something the lead has to remember.
   - Any worker can be replaced by a fresh one that rebuilds context from the task file and the branch.
4. **Judgment goes in at the objective, before the code.** The lead's intake produces a brief the user approves before any code is written: one objective a single task can reach, the gates that show it's met, the facts a worker needs, and a size estimate. It says nothing about how to meet the objective. The design is the worker's, held to the project's rules (AGENTS.md, the user's CLAUDE.md, these principles), which the worker follows and automated review applies before the user reads the diff. A gate measures the objective, never a way to it, so no gate stands between a worker and a better design. `crew ready` refuses a brief that says how, and `crew dispatch` one readied before briefs left that out.
   - **Goal tasks are the exception.** For the tasks of a goal the user started, the brief review and the goal lead stand in for the user's approval of the brief, so the user's judgment reaches the work at the PR instead. A wrong objective there costs a PR the user closes, not a brief the user fixes. Parking keeps the decisions that are expensive to undo with the user: anything irreversible, anything outside the goal, and any brief-review finding the goal lead can't settle with confidence.
5. **Throughput is capped by review capacity.**
   - `MAX_WORKERS` limits concurrent sessions.
   - A goal's `max_in_flight` (`GOAL_MAX_IN_FLIGHT` unless set) limits its dispatched-but-unmerged tasks, including open PRs and every task of a stack. Goals are where work outruns review: a goal lead readies tasks with nobody watching, and a stack it builds on a wrong turn has to be undone PR by PR. The lead's own tasks need no such cap, since the user approves each dispatch.
   - `crew dispatch` enforces both under the ledger lock.
6. **The user is the only one who merges.**
   - The agent prompts say exactly what each agent may do on GitHub. For workers that is: push their own task branch (with `--force-with-lease` allowed after a rebase), open a PR, edit it, post its automated-review summary, mark it ready after its first hand-over, rerun their PR's failed CI jobs once, post what they found about red CI, and publish evidence files for their own task to the project's evidence repo with `crew evidence`. Merging stays with the user.
   - We rely on the prompts for GitHub behaviour and don't try to parse shell commands for it; that approach can't be made complete. `deny` rules in the settings files catch the obvious mistakes (`gh pr merge`, `git push --force`, `gh run cancel`). Branch protection, where the repo allows it, is the real backstop.
   - File edits are enforced mechanically: `crew guard` checks Edit/Write paths. Bash isn't sandboxed (see [Bash](#bash-no-sandbox)). Workers run it in auto mode, the same trust you give your own sessions, and the gardener only runs its read-only allow list and `crew remember`.
7. **Project-agnostic agents, project-specific conventions.**
   - Agents live at user level (`~/.claude/agents/`).
   - Project conventions come from the repo's `AGENTS.md`/`CLAUDE.md`, which Claude Code loads automatically for every session in the repo. The lead and brief-reviewer, which run outside every repo, read it explicitly. The user's personal taste goes in `~/.claude/CLAUDE.md` or `~/.claude/rules/`.
   - Facts about a project that the user approved, and that collaborators shouldn't see or that would be lost in a merged task's Decisions, go in its project memory in the ledger (see [Project memory](#project-memory)).
   - Agent prompts should stay generic.
8. **One machine runs the crew at a time.**
   - The home's `host` file names it, and a git push claims it, so two machines can't both believe they hold it.
   - Every change to the ledger checks it, and so does everything that starts a session, so two machines never dispatch the same task. Other machines only read.
   - Moving the crew is `crew host up --take` on the new machine. Work in flight carries on there with fresh workers: sessions stay behind, but task files and pushed branches don't.
9. **Plain words.**
   - Each concept gets an ordinary word, used in its ordinary sense: lead, worker, task, goal, proposal, memory.
   - A new concept gets a word a newcomer would guess right, not a coined term or a metaphor that needs a glossary.
   - Existing terms stay, crew's own among them (ledger, brief, gardener, stack and restack, crew home, goal lead, host). This principle is for what's added.
10. **Small and quiet.**
    - crew is one Go binary on the standard library, the agent files, and plain text. The one exception is Charm's modules for `crew status`'s live view: it uses bubbletea and lipgloss, and may add bubbles. There's no database. The dependency rules are in `CLAUDE.md`, under Conventions.
    - Plain `crew` commands on timers coordinate the work, not agents supervising agents. crew starts a worker, a goal lead, the gardener or the misses agent only when there's work for it: see [`crew tick`](#crew-tick) and [Gardener](#gardener) for when. The [review eval](#review-eval) runs only when the user runs it. So a crew with no work sends no model requests of its own. For the gardener, new commits on the default branch are work, whoever made them; for the misses agent, a newly merged task with the user's comments after an automated review.
    - Two processes stay up while the crew is idle, and both are Claude Code's. One is the lead's Remote Control server (`crew serve`, the `crew-lead` service), which waits for you to open the lead from your phone. The other is the daemon that `claude --bg` hands workers and goal leads to, which outlives them. Claude Code's docs don't say either one uses the model while it waits (see [Assumptions](#assumptions-to-re-check-when-claude-code-updates)).

## Repository layout and where each file installs

A clone of this repo is a **crew home** (`~/crew` by default): `crew` runs from its `bin/`, reads its `config/` and `templates/`, and keeps the ledger under `projects/`. `crew install` links `crew` and `lead` into `~/.local/bin`, and copies only what Claude Code, fish and systemd (launchd on a Mac) have to find elsewhere.

This repo is the public one, and never contains state: nothing under `projects/` but `.gitkeep`, and no `reports/`, `config/crew.env` or `host`. A person's private home adds those (see [Runtime state](#runtime-state-created-by-use-never-shipped)), so merging a new public version into it never conflicts on them.

## Main flows

### Intake and dispatch
```
you ⇄ lead (a session in <home>/lead, for one project or every one; reads code in crew checkout <p>)
  lead: confirm goal → crew new "<title>" --branch <name> → investigate
        → its kind: a fix only for a defect live in production, naming fixes and missed_by (see "Fixes")
        → what's still to learn, if anything: spikes (see "Spikes") → the objective, with its risk tier → its gates (Acceptance criteria)
        → size estimate (## Size); past MAX_PR_LINES or two concerns → split ("Splitting a task")
        → brief-reviewer subagent in the background (task file path only) → summary right away
        → review arrives → findings settled in the brief, never as a gate on the method → Raise findings to you
        (each point written into the draft task file as it's agreed)
  you: "go"                             # if the review is still running, the lead dispatches once it's settled
  lead: crew ready TASK                 # checks the sections and keys its kind needs (a build: Goal / Acceptance criteria /
                                        #   Size, and a risk tier) and the ones it leaves empty (a build: Structure / Plan /
                                        #   Constraints and conventions), the criteria are '- ' items,
                                        #   and no item still to learn is open (its records)
        crew dispatch TASK
          ├─ lock; check status, the brief says nothing about how (as crew ready), with --tick (crew tick's) that tick
          │     still dispatches it (tickDispatches), depends_on (same project, must be merged or done),
          │     MAX_WORKERS, the goal's max_in_flight; unlock
          │     a stacked task's parent is exempt from "must be merged or done";
          │     a parent that has already merged → base rewritten to its base
          ├─ git fetch origin <base> (must succeed for a stacked task: the parent's branch has to be pushed);
          │   create ~/agent-work/<p>/<id> on a new <branch> from origin/<base>, recorded as base_sha:
          │     WORKTREE_TOOL=git        git worktree add --no-track -b …
          │     WORKTREE_TOOL=worktrunk  wt switch --create … --no-cd --format json --config-set worktree-path=…
          │                              (runs the repo's pre-start hooks; output → logs/worktree-<p>-<id>.log)
          ├─ copy WORKTREE_COPY files
          ├─ lock; record worktree; repeat the checks
          ├─ cd worktree; claude --add-dir <home> --bg --agent implementer --permission-mode … \
          │     --autocompact <WORKER_AUTOCOMPACT_WINDOW> --settings <worker settings, env: project and home> --name crew-<project>-<id> "<prompt>"
          ├─ strip color codes; parse "backgrounded · <job>"; poll `claude agents --json --all` until the job's
          │     process reports a session ID that starts with the job ID (job `failed` → stop, record nothing)
          └─ record worktree, worker_name/job/session; status → working
```

Size is checked against one setting, `MAX_PR_LINES`, three times: at intake, where the brief's `## Size` is the lead's estimate and the brief reviewer's Size question checks it against the code; by the worker on its real diff before it opens a PR; and again when its automated review doesn't converge (both below).

### Worker first run
The worker reads the task file, then implements with commits, pushing its branch after each one so its work is never only on one machine, and runs the checks from `AGENTS.md`. When its plan changes existing code that no test covers yet, refactors included, its first commit adds tests that pin its behaviour as it is, and it logs that commit's SHA (`Pinned in …`) or why it skipped the pin. Once the checks pass, it checks its base with `crew check-base TASK` before each step that reads the branch and costs a lot: the exhale, the pre-PR review, the evidence and each automated review (see below). Then, if `crew config PRE_PR_REVIEW --task` says `yes` (always, for a high-risk task), it runs `/simplify` on its branch's changes, starting that skill's review agents (`general-purpose` agents) on Sonnet, not on its own model, keeps what stays inside its change as a commit of its own, and logs what it folded (`Exhale: …`). Then it checks the branch's size once, against `MAX_PR_LINES`: past it, it goes to "Workflow: split proposal" (below) instead of opening a PR. Next it spawns casual-observer (if `crew config PRE_PR_REVIEW --task` says `yes`), fixes the findings it agrees with, design ones included, asks the user about one whose fix would cross a bound (a gate, Out of scope or a project rule), and logs the ones it declines, with its reasons, under "Findings declined" for the lead to pass on. A high-risk task's worker then runs Claude Code's `/security-review` and records what came of it as `### Security review` under `## Evidence`. For each acceptance criterion it runs what shows it holds and records the command and its output under `## Evidence`, one `### <n>.` entry per criterion. Screenshots and other files a reviewer should open never go on the branch: when the project has an `EVIDENCE_REPO`, the worker publishes them with `crew evidence` and puts the Markdown line it prints for each in the entry, so they show on the PR. It pushes, runs `gh pr create --draft` (a draft whatever `pr_mode` says, until the hand-over) with a body filled in from `templates/pr-body.md`, its Evidence built from the task's, and records the PR with `crew set TASK pr …` and `crew log`.

Then, unless its task's `AUTO_REVIEWS` is 0, it reviews its own PR. It reads that with `crew config AUTO_REVIEWS --task`: the project's, or 0 when the lead turned the task's `auto_review` off at intake and the task isn't high risk.

```

              → readTaskPRs and git fetch origin, then refuseOffBase under the lock, as the first hand-over below
              → refused: the rebase, push and retarget to run (Workflow: restack), then check again

              │    the rebase, alone (onBase), or, for an unstacked branch that doesn't start on its base, a word
```

The risk tier is the lead's call at intake; `raiseRisk` only checks it against the diff. It works on the project's clone, without the worktree: `git diff --name-only` from where the branch left `origin/<base>` to the branch, limited to the `SENSITIVE_PATHS` pathspecs, so git does the matching. It looks at the local branch and origin's, after a fetch, since either may have commits the other lacks: the worker's own commits are in the local branch (its worktree is on the clone), and a suggestion applied on GitHub only on origin. For a stacked task whose parent was rebased, or whose merged parent's branch is gone from origin, the diff starts at `base_sha` instead, as a restack cuts there, so the parent's changes aren't counted as the task's. A check that fails (a fetch, no merge base, a pathspec git rejects) refuses the hand-over. It runs again at every `crew sync`, so a commit after the hand-over raises the tier too; that can't refuse anything, so `crew status` says `not yet: no security review yet` in the row's merge check instead, and the lead sends the worker back to run the review before it hands over again. Nothing lowers a tier. `crew status` gives each `pr-open` row the look its tier asks for (`lookNote`), and ends each project with a `to review:` line, its open PRs cheapest look first, then by number (`toReview` sorts them into the report, and the printer words the line).

A pass that didn't converge ends in a question, never another review, so no pass runs more than `AUTO_REVIEWS` reviews without an answer: the user's, or in a goal the goal lead's. When the branch is past `MAX_PR_LINES` or holds two concerns, it's the split question, the one a worker also asks before a PR past `MAX_PR_LINES`, in the implementer's "Workflow: split proposal": the worker says what got in the way, proposes smaller pieces to replace the branch (each naming the commits and paths it carries over), and asks under Open questions: split as proposed, review it anyway, or take it as it is. The question takes the usual path to the user, or in a goal to the goal lead, which answers it: to split, it opens the pieces with `crew new … --goal`, moves the tasks stacked on or depending on the old one to the pieces, and abandons it (`lead.md` "Splitting a task"). Otherwise the branch has nothing to split, and the worker asks only whether to review it anyway or take it as it is.
That's the first pass of automated review. A review round with an `Automated review requested` line (below) has the worker run another, once it has addressed the round's comments. A pass is the reviews after the last `Summary posted`, derived from the record rather than stored: it runs up to `AUTO_REVIEWS` reviews (at least one when the user asked for it), numbered on from the last pass, and posts a summary comment of its own.

**Before the first hand-over, a task's own worker moves its branch and PR.** A parent can get new commits or merge while its child's first run is still making the branch, and the lead can move a task to another base (`crew set TASK base`). `crew hand-over` is where every first run ends, so that's where crew checks (`refuseOffBase`), and the worker makes the same check earlier, with `crew check-base TASK`, before each costly step of its first run: `/simplify`, the pre-PR review, the evidence and each automated review. Each of those reads the branch, and a rebase after it would leave a review of commits the PR no longer holds, to be paid for again. `crew check-base` reads the PRs (`readTaskPRs`) and fetches as the first hand-over does, runs `refuseOffBase` under the lock, and says `nothing to move: carry on` when it passes; it refuses a task already handed over, since `crew tick` restacks those. Both refuse while a stacked branch doesn't hold the parent's latest commit, or the PR targets another branch than the task's base, and the refusal is what `crew restack` would send: the restack note's rebase and leased push (`rebaseFor`), plus, after a merge, the base to record and the PR to retarget, or a retarget alone (`afterPush`, `retargetReason`, `onBase`). It reads the PR and the parent's PR from GitHub and moves `base_sha` first, as `crew sync` would, so a PR the worker just moved, a parent that just merged, or a branch the worker just rebased, isn't judged by what sync last saw. The worker runs them in its own session, on its own model, keeps its uncommitted work, and carries on. `crew tick`, `crew restack` and `crew sync` leave such a task alone and say so (`movesBeforeHandOver`): a fresh restack session would take over a session mid-way through its own work. A worker idle before it reached the hand-over is nudged as any stalled worker is, and meets the refusal at its next check. The check runs before the one for a PR, since a merged parent's deleted branch can't take one. The hand-over's own check stays for a parent that moves after the worker's last `crew check-base`. A rebase after the automated review would still leave the review describing other commits than the PR holds, so the first hand-over also refuses a newest review that read from another fork point than the branch's now, or whose head the branch no longer holds (`staleReview`). It accepts a head the branch still holds, since a fix-later or nitpick fix may follow the last review (implementer "Workflow: automated review" step 3). Later hand-overs skip both checks: a restack is crew tick's then, and a review round's new commits aren't automated review's.

With `AUTO_REVIEWS` at 0 it goes straight from opening the PR to `crew hand-over`. A task's `auto_review: no` doesn't hold once the task is high risk (`AutomatedReviewOff`), so crew works that out from `risk` rather than storing it: a raise (`raiseRisk`) logs that review is back on, and `crew hand-over` refuses such a task until it records a review. The hand-over is the only way into `pr-open`, since `crew set` refuses that status, so every later move there, after a review round, a restack or a question, checks the branch as it is then. Only the first marks the PR ready.

The task file's record holds the loop's whole state, so a worker resumed or compacted in the middle carries on from it. If it gets blocked, it writes an Open question, sets `status needs-input`, and ends its turn with the question.

### Spikes
A draft whose objective or gates rest on something nobody has checked has each question as an item still to learn, a record crew keeps beside the task file (see "Records" under `crew` internals), and `crew ready` refuses it until every item is settled. A **spike** answers one by trying a path:

```
lead: crew to-learn DRAFT "<question>"   # an item still to learn: a to_learn record; prints its ID
      crew new "<what it tries>" --kind spike --informs DRAFT [--goal GOAL]   # refuses an informs that isn't a draft
      brief: Goal (the question), Plan (what to try, a time box), Acceptance criteria (what would answer it)
      crew ready SPIKE      # no Size, no risk, and its Plan is allowed: the kind tries a path
      crew dispatch SPIKE   (or crew tick, for a goal's)                  # in flight while it runs, like any task
worker: first-run steps 1-3 → "Workflow: spike": try the path, commits local only → "## Report", first line "Answer: …"
        crew hand-over SPIKE → checks the answer (handOverReport) → status done
crew tick: a done task's worktree and local branch → crew cleanup
           a goal's done spike, report_sent not yes → crew goal followup: "<spike> reported: <answer>; it informs <draft>"
lead or goal lead: crew learned DRAFT ITEM "<the spikes' answers, side by side>" (a learned record) → finish the brief
```

- **What a kind asks is one table**, `kinds` in `ledger.go`: the sections `crew ready` needs, whether it makes a PR (`pr`: then it needs a risk tier and takes part in stacks), the other front-matter keys it needs set (a fix's `fixes` and `missed_by`), each checked as `crew set` checks it (`checkValue`), the link key `crew new` may set and the status the linked task must have (a spike's `informs`, a draft; a fix's `fixes`, a merged task or `unknown`), and the check `crew hand-over` runs and the status it moves to. `crew new`, `crew ready` and `crew hand-over` ask the task's rules (`Task.rules`) and never a kind's name. A task without a `kind` is a build.
- **A spike leaves nothing in the shared repo.** Its worker never pushes, and opens no PR: the code is thrown away, and the report in the ledger is the record. So nothing needs cleaning up on origin, and `crew cleanup` deletes the local branch as it does a merged task's (`Status.Delivered`: merged or done). `crew hand-over` refuses a spike whose worktree has changes it didn't commit, since cleanup skips a dirty worktree. `crew sync` looks for no PR for a spike: one under its branch's name would be an old one, and could mark it merged. A spike takes no part in stacks: a restack has its worker push, and a task stacked on it would wait for a branch that never reaches origin. So `stackRefusal` refuses both ways up, wherever a stack is made: `crew new --on`, and `crew set` of a `base` or a `kind`. A plain `depends_on` a spike clears once it's done (`pendingDeps`).
- **`done` always means the report is there**: only `crew hand-over` sets it, after `Task.Answer` finds the answer line, and `crew set` refuses it. So the goal lead is never told of a report that doesn't exist, and `report_sent` keeps it from being told twice.
- **Spikes count toward `max_in_flight`** while they run. Not counting them would change what the cap is for (principle 5); they're short, and `MAX_WORKERS` counts them either way.
- **The answers are put side by side by whoever owns the draft**, not by the spikes' workers: workers never edit other tasks, and weighing several answers is a judgment. Outside a goal, `crew status` shows the draft's open items and its spikes on its row.

### Fixes
A **fix** is a build for a defect live in production; any other correction is a **refine**, with a build's rules. The two keys a fix needs let a later count trace each fix to the task that caused it and to the check that missed it:

```
lead: crew new "<title>" --kind fix [--fixes TASK|unknown]   # refuses a TASK that isn't merged
      crew set FIX fixes TASK|unknown; crew set FIX missed_by <check>   # one of missedBy in ledger.go
      crew ready FIX        # a build's brief, plus fixes and missed_by
worker: step 4: a failing test that reproduces the defect, committed before the fix → ## Evidence shows both runs
```

- **A short list, not free text, for `missed_by`**, so the misses can be counted. A new check joins the list when one exists.
- **crew doesn't check the order of commits.** It can't tell a test from a fix in an arbitrary repo; the evidence of the two runs is what the user checks.

### Stacked tasks
A task is *stacked* when its `base` is another task's `branch`; that task is its *parent*. Nothing else records the relationship (`parentOf` looks the base up among the project's task branches), so it can't disagree with `base`, and `crew set TASK base <a task's branch>` stacks an existing task. `depends_on` stays as it was written.

```
crew new "<title>" --on PARENT   # base = parent's branch, depends_on = parent; refuses a finished parent or a spike
crew dispatch TASK               # needs origin/<parent branch>, not a merged parent; records base_sha = the parent's tip
worker                           # gh pr create --base <parent branch>; PR body starts "Stacked on #N."
crew sync                        # the PR pass records pr_base (baseRefName); then git fetch origin (only for
                                 #   projects with a live stacked task, SENSITIVE_PATHS or a PR on another
                                 #   branch), move base_sha forward, print "<task>: needs a restack,
                                 #   <parent> moved|merged" and, for any task, "<task>: PR targets <pr_base>,
                                 #   not <base>"
crew status                      # children listed under their parent, with "needs restack: …"; a pr-open row's merge check
                                 #   says "PR targets …" and "stacked on …";
                                 #   a ready child of a parent in flight is listed on its own, "on <parent>"
crew restack TASK                # nothing to rebase but a PR to retarget → a "Retarget (…)" note: gh pr edit --base <base>;
                                 #   no rebase, never waiting on the parent; not twice (retarget_sent) unless --again
                                 # otherwise refuses while a live parent needs a restack itself (bottom-up),
                                 #   and a restack onto the commit it already sent (restack_sent) unless --again
  ├─ git fetch origin; target = origin/<effective base>:
  │     parent unmerged → the parent's branch; parent merged → the parent's base, following merged parents
  │     upwards (the default branch when a stack merges bottom-up)
  └─ crew followup TASK --note "…git rebase --onto <target sha> <base_sha>…
                                  git push --force-with-lease=<branch>:<origin/<branch> sha> origin <branch>…"
worker: rebase → checks → the note's push, as a command on its own
        → if the base changed: gh pr edit --base <new>; crew set TASK base <new>
        → if the PR targets another branch than base: gh pr edit --base <base>
        → crew hand-over TASK if it was pr-open, else its status as it was
```

- **`base_sha`** is the newest commit of the parent's branch that the task's own branch contains, the cut point for `git rebase --onto`. `crew dispatch` records it and `noteBaseSHA` (from `crew sync` and `crew restack`) moves it to the two branches' merge base. Once the parent is squash-merged or rebased, that merge base falls back to a commit before the parent's work, so the recorded value is kept for as long as the task's branch still contains it. When it moves, the old value goes to the front of `earlier_base_shas`, so `crew hand-over` can still find where the work in evidence from before the restack starts (`workIn`). Only `crew` writes either.
- **Whether a restack is needed is computed, never stored** (`restackReason`): the parent is `merged` or `abandoned`, or `origin/<parent branch>` isn't an ancestor of the task's local branch. It reads the refs as last fetched, so `crew status` is as fresh as the last `crew sync`.
- **Whether a PR needs retargeting is a question of its own** (`retargetReason`): the task is in flight with an open PR, `pr_base` (what `crew sync` last read from GitHub) isn't empty and isn't the branch the task belongs on now (`effectiveBase`: its `base`, or what a merged parent merged into, where GitHub moves the PR itself when it deletes the parent's branch), and `origin/<that branch>` exists, since GitHub can't target a branch it doesn't have. `crew sync` fetches for such a PR, so a branch pushed from elsewhere is seen. It applies to any task with a PR, stacked or not, and makes no GitHub call. `restackReason` doesn't consult it, so a parent whose PR targets the wrong branch never holds back its child's rebase. A rebase note carries the retarget whenever it's due; a retarget alone goes out only when the branch needs no rebase (`onBase`): a stacked task's holds its parent's latest commit, and an unstacked task's starts on its base (`base_sha` is on it). crew never rebases an unstacked task, so one whose branch doesn't start on its new base (moved to `main` off an abandoned parent, say) gets no note, and `crew restack` says why. This is what lets the lead move a task with `crew set TASK base` alone.
- **Before its first hand-over, a task isn't crew restack's.** Its own worker moves the branch and PR when `crew check-base` or `crew hand-over` refuses (see "Worker first run"), so `crew restack` refuses it (exit 4), `crew tick` holds it back and says why, and `crew sync` names who moves it.
- **A restack runs in a fresh session on Sonnet** (`startRestack`, `launchRestack`), which takes over as the task's worker. Resuming the worker's own conversation cost far more than the rebase: a median of 491k weighted tokens a restack on this machine, in November 2026, mostly for rereading a long context. The session gets the restack note and the task file's path, and nothing else: an unsent round, or word of a pause, waits for the next followup, which starts afresh on the task's model: the restack session's fingerprint takes in its prompt, so `followup` tells it from a worker's, even on a task whose own model is Sonnet, and gives that as the reason. It starts only while the task is `pr-open` and its worker isn't busy, and once the worker's process has closed (`launchSession`). A conflict with an unstacked task's base isn't a restack: `crew catch-up` sends it to the worker as a round.
- **The worker changes `base` and the PR's base, last.** `crew restack` returns as soon as the restack session has started. If it rewrote `base` itself, a rebase that then failed would leave a task that no longer looks stacked, with the parent's commits still in it.
- **A goal's `max_in_flight`** (`goalInFlight`) counts every task of a stack, as `MAX_WORKERS` counts every session. A deep stack is the case it's for.
- **`restack_sent`** is the commit the last `crew restack` asked the worker to rebase onto, and **`retarget_sent`** the base it last asked the worker to point the PR at. `crew restack` refuses to send the same one again unless `--again`, so a worker that couldn't restack isn't sent the same note in a loop. Only `crew` writes them.
- **`crew sync` never restacks.** `crew tick` does, through `crew restack`. Nothing restacks a whole stack at once: each restack is a background worker, and the next task up only needs one after the worker below it has pushed.
- **`crew observe TASK`** compares against `base_sha` when `origin/<base>` is gone.

### Sync and cleanup
- `crew sync` finds missing PR URLs by branch (`gh pr list --head`), records `pr_state`, `pr_base`, `pr_updated`, `ci_state` (from `statusCheckRollup`, by `rollup` in `cmd_ci.go`), `mergeable` (`conflicting` when GitHub says the PR conflicts with its base, `unknown` while it works that out) and `merge_state` (GitHub's `mergeStateStatus`, in lower case), and sets `status: merged` when GitHub says merged. Then, for each task in flight, it raises the risk of one whose branch touches a sensitive path (`raiseRisk`, see "Worker first run") and checks the stacks and each PR's base, as above. A project it can't load, with no clone on this machine say, holds up no other: sync names it, skips it, and exits 1 once it has synced the rest.
- `crew cleanup TASK|--merged` stops the worker and removes it from agent view (`removeSession`), then ends any background process still running in the worktree (`stopProcessesIn`: TERM, then KILL after 10 seconds), then removes the worktree (`git worktree remove`, or `wt remove --no-delete-branch --foreground` so the repo's remove hooks run) and deletes the local branch (merged tasks and done spikes only: `Status.Delivered`). It removes the worktree the task file records and any at the task's own path `$WORK_ROOT/<p>/<id>`: a failed Worktrunk dispatch leaves one there, unrecorded, and its branch goes too when it has no commits of its own. A task with no worktree anywhere gets no ledger change and no log line. The worker goes first so that it doesn't carry on in a deleted directory. Its leftover processes go next: a dev server it started in a background shell outlives `claude stop`, and would otherwise keep running, holding its port, after the worktree is gone. They're found by working directory: in `/proc` on Linux, with `lsof` and `ps` on a Mac. Only processes without a terminal are ended: one with a terminal is the user's, such as their shell sitting in the worktree. crew's own process and those that started it are left alone too. A worker whose process won't close keeps its worktree until a later cleanup; one that `claude rm` won't delete only gets a warning. A task whose worktree stays (not finished, uncommitted changes, a worker that won't stop, a remove that fails, such as a directory that isn't a worktree) is warned of last, as "<task>: worktree stays: <why>", and cleanup exits `exitNotYet`; crew tick then holds back that line rather than reporting the worktree cleaned up, so the leads hear it once. Cleaning up a merged parent is safe while tasks are still stacked on it: their branches contain its commits, a restack cuts at `base_sha`, and nothing reads the parent's local branch.

### `crew tick`
One pass over every project, run by `crew-tick.timer` every 3 minutes (the `crew-tick` job on a Mac), by the lead (at session start and for status), or by hand. A second tick while one runs exits at once (it doesn't wait for `.crew-tick.lock`). Each step is a `crew` command run as a process of its own, so one that refuses doesn't stop the rest. It prints one line per thing it did, and one per thing it holds back, with why; nothing otherwise. It keeps both for the leads (see [What the lead hears](#what-the-lead-hears)).

```
crew tick
  ├─ git fetch origin (soft). origin's host names another machine, and this one held the lease
  │    → stand down: crew-* sessions stopped, unpushed ledger work kept on
  │      lost/<host>-<time>, home reset to origin, services disabled; nothing else happens
  ├─ require_host: this machine holds the lease, or the tick stops
  ├─ crew sync --all: names any project it can't load, which the rest of the tick skips
  ├─ crew mcp sync: every project's mcp.local.json, then lead/.mcp.json
  ├─ for each task (a paused project's get only cleanup, feedback, ci-fix, catch-up and needs-input):
  │    merged or done, worktree still recorded   → crew cleanup (exit 4: held back, with why it stays)
  │    in flight, PR changed since last read     → crew feedback (the user's comments → a round;
  │                                                  collaborators' → unchecked Open questions)
  │    pr-open, ci_state failing                 → crew ci-fix: reads the head's checks again; once all have finished
  │                                                  and one failed, a round "CI failed on <sha>", once a head; past
  │                                                  MAX_CI_FIXES rounds the branch caused, an unchecked Open
  │                                                  question instead
  │    pr-open, unstacked, mergeable conflicting → crew catch-up: reads the PR again; while it conflicts with the
  │                                                  task's base, a round "Conflicts with <base> at <sha>", once for
  │                                                  each commit of the base on origin (git ls-remote)
  │    working or addressing-feedback, its job   → crew followup --fresh --note "This task moved to <host>…"
  │      unknown here and no worktree here          (moved_here: a task that moved here; next tick its new job is listed)
  │    worker busy (mid-turn, or a prompt open)  → stop here, holding back what it would send; the next tick tries again
  │    review_rounds > last_round_sent           → crew followup
  │    interrupted (a pause cut its turn short)  → crew followup, which tells it to carry on
  │    working or addressing-feedback, no Open   → crew nudge: resumes it once to carry on; stalled again with
  │      question, worker not stopped, its turn     no new commit or change of status, or no worktree here,
  │      ended and its transcript 8 min quiet      → an unchecked Open question for the lead instead
  │    an unchecked nudge question, worker moved   → crew settle: checks it off, and a needs-input task
  │      on since (commit, status, followup)          waiting on nothing else goes back to its old status
  │    pr-open, needs a restack, parent doesn't, → crew restack (held back, with why, before the first hand-over,
  │      and restack_sent isn't the target yet      when the task isn't pr-open, its parent's restack comes first,
  │                                                 or its parent was abandoned)
  │    pr-open, no rebase needed, PR targets     → crew restack (a retarget alone)
  │      another branch, retarget_sent isn't base
  │    not needs-input, unchecked Open questions → crew set TASK status needs-input
  ├─ for each running goal:
  │    a note, a worker question it hasn't had,  → crew goal followup, once the goal lead is free and its project
  │      a spike's unsent report, or interrupted    isn't paused (held back, with why, until then)
  │    every task finished                        → crew goal done
  ├─ dispatchReady: the ready tasks of running goals, and those outside a goal whose
  │    go-ahead is met (tickDispatches), every unpaused project's together,
  │    highest priority first, then by project and ID (sortForDispatch)
  │    waiting on other tasks (pendingDeps)     → held back, naming them
  │    the rest                                  → crew dispatch, each in turn (exit 4, a dispatch that has to
  │                                                  wait: held back with its reason, and the next task is tried)
  ├─ news/held-back: what this tick held back, replacing the last tick's
  └─ push_ledger in the foreground (soft): whatever a background push missed
```

The stand-down and the lease check are gates, not steps: they decide whether the tick does anything, so they run in the tick's own process rather than as `crew` commands of their own.

- **One rule for "waiting on you":** a task whose worker is idle and that has an unchecked item under Open questions is `needs-input`. `crew tick` sets it, and clears it only for a question crew asked itself: `crew settle` checks off a nudge question once its worker moves on, and puts the task back in the status it had before `needs-input`. Whoever settles any other last question sets the status back: the worker when it's resumed with the answer, the lead otherwise. Going back automatically for those would hide the questions of workers still running on a prompt from before questions were checkboxes.
- **A worker whose turn ended mid-task is nudged, once** (`crew nudge`). A worker waiting on the user sets `needs-input`, so a turn that ended while the task still says `working` or `addressing-feedback`, with no Open question, ended by mistake (see "Stalls" under Assumptions to re-check). That holds whatever `claude agents` lists for it, short of `stopped`, which a pause or the user did on purpose. The transcript must have been quiet for 8 minutes (`stallAfter`), since a worker you're talking to through `crew attach` ends its turn after every reply, and a resume ends the attach. Only a new commit on the branch or a change of status counts as progress after a nudge: a worker could answer every nudge with a Log line. A second stall without either becomes an Open question for the lead, naming the branch's head and the worker's transcript, which outlives its process. So does a stall whose worktree isn't on this machine: making it again can take minutes of a repo's hooks, and `crew followup --fresh` does it once the lead asks. The question stands until its worker moves on, and `crew tick` runs `crew settle` first for any task with one open: it checks the question off with `Settled: <what>` (a new commit since the question's head, a status change to anything but `needs-input` (tick's own mark for the question isn't one), or a followup logged since), logs `nudge question settled: <what>`, and puts a `needs-input` task with no question left back in the status it had before (`statusBeforeNeedsInput`): its worker's turn, or `pr-open` when tick marked a handed-over task. Only nudge questions are settled this way (`nudgeQuestionStart`): a worker's own, a collaborator's and a CI or conflict question wait for a person. A question about a missing worktree has no commit to compare, so only a status change or a followup settles it. `crew nudge` reads `claude agents` again under the ledger lock before it resumes anyone, so a worker resumed since tick looked isn't nudged.
- **Rounds wait for the end of the worker's turn.** Delivering one mid-turn would need `SendMessage`, which only a Claude session can call.
- **Only changed PRs are read.** `crew sync` records each PR's `updatedAt` as `pr_updated`, and `crew tick` runs `crew feedback` only when that is newer than `feedback_since`. A quiet PR then costs one API call per tick instead of four.
- **Nothing is sent twice:** `last_round_sent` for rounds, `restack_sent` for restacks, `retarget_sent` for retargets, and a nudge's Log line, `nudged: turn ended mid-task at <short sha>`, for nudges, until a new commit or a change of status. Red CI is recorded once for each head commit: the `CI failed on` and `CI is still red on` lines in the task file are the record (`Task.CIReported`), not a key. So is what the worker found: `crew ci-summary --not-the-branch` ends the round's line with `(the branch didn't cause it)`, and such a round doesn't count toward `MAX_CI_FIXES` (`Task.CIFixes`). A conflict with the base is recorded once for each base commit, the same way: its `Conflicts with` line is the record (`Task.ConflictReported`).
- **CI is the worker's own business until it hands the PR over.** `crew ci-fix` acts only on a `pr-open` task whose PR is still open and whose head's checks have all finished, so a red build while the worker is still at it, or before a rerun ends, isn't sent. `ci_state` only spares a tick the call while CI isn't failing; `crew ci-fix` reads the checks again and decides.
- **So is a conflict with the base, and after the hand-over it's merged, never rebased.** `crew catch-up` acts only on a `pr-open` task that isn't stacked, whose PR is open, targets the task's base and conflicts with it; `UNKNOWN` (GitHub still working it out) waits for a later tick. The base commit is the base branch's tip on origin (`git ls-remote`), not GitHub's `baseRefOid`, which can lag behind it. The worker merges the base in and pushes without force, so the commits the user may have reviewed stay as they were. A stacked task's conflicts are a restack's. `mergeable` is crew tick's filter, like `ci_state`, and what crew status goes by when it can't read GitHub; neither acts on it without reading the PR afresh.
- **Dispatch comes last.** A review round resumes an idle worker, and a restack starts a fresh one in its place, without checking `MAX_WORKERS`, and a merged task's cleanup can stop a worker that is still busy. Dispatching after every other step means `crew dispatch`, which counts busy workers afresh, sees what this tick has already done. Rounds and restacks still don't check `MAX_WORKERS` themselves, so one sent while every worker slot is taken puts the crew over it until that worker's turn ends.
- **A task's `priority` orders the dispatch** (a whole number, higher first, empty is 0; set with `crew set`). It's one order across every goal and project, because `MAX_WORKERS` counts busy workers across them all: a free worker slot goes to the highest-priority task that its caps and dependencies let through. A task they hold doesn't hold back the ones after it, since caps are per goal and dependencies per task. (A project can set a lower `MAX_WORKERS` of its own, which holds back its tasks while another project's go ahead.) A value written by hand that isn't a whole number counts as 0, with a warning.
- **Outside a goal, tick dispatches only on a go-ahead.** The user's word to dispatch a task once another reaches `pr-open`, `merged` or `done` is its `go_ahead` key (`GoAhead`), which the lead records with `crew set`; the lead never watches for the moment itself. It's met once the other task's Log has the status line, or that task is merged or done, so a task that went past the status between two ticks still counts, and an abandoned one never does. It lasts only while the task is `ready`: `Task.SetStatus` clears it on any other status, so a task sent back to draft and made ready again needs a new word. Dispatching ends it the same way, and the news says what it was. Tick runs `crew dispatch --tick`, which checks `tickDispatches` again under the lock once the worktree is set up, so a go-ahead withdrawn or a goal abandoned meanwhile starts no worker.
- **A paused project gets nothing new** (see [Pausing](#pausing)). The tick checks each project once, and holds back the steps that would start a session, saying so: followups, restacks, goal followups, dispatches. The ones that only record still run.
- **Restacks need no word from the user any more.** `crew sync` still never restacks; `crew tick` does, bottom-up, only for a task that has been handed over, is `pr-open` and whose worker is idle. Before the first hand-over, `crew check-base` and `crew hand-over` have the task's own worker do it. A restack force-pushes the task's branch.

### What the lead hears
A lead hears, with each message the user sends it, what crew did since the previous one, and what `crew tick` is holding back. It doesn't have to run `crew tick` to find out, or wait to be asked.

```
crew tick, each thing it did                     → news/<day>.log: the time, the project, the line
crew set TASK status, crew hand-over, run by a   → news/<day>.log, the same way
  worker or goal lead
crew tick, what it held back                     → news/held-back, replaced at the end of each tick
crew lead --hook (SessionStart, UserPromptSubmit) → the news since the session's previous prompt;
                                                    its record is news/sessions/<session_id>
```

- **A session hears nothing from before it started.** Its start (SessionStart) or, failing that, its first prompt only begins its record: the time, and the held-back lines as they are. Each prompt after that hears the lines written since the record's time, then the held-back lines it hasn't been told. Each session keeps its own record, so two leads each hear everything.
- **No line is missed.** A line is timed and written under `.crew-news.lock`, and a session reads the news and moves its record's time under it too, so no line can land behind a time a session has already passed.
- **A held-back line is told once while it's held back.** The record keeps the held-back lines the session has been told, and drops one once a tick no longer holds it back. A reason that changes is a new line, so it's told; a task held back again later is told again.
- **Each lead hears its own scope:** `CREW_PROJECT`, so a lead for one project hears that project and the phone lead (`all`) hears every one, with each line's project before it, since two projects can have tasks of the same name. A line about every project (a stand-down) reaches every lead.
- **Only leads hear it.** Workers and goal leads have an empty `CREW_LEAD_FINGERPRINT` (`inWorkerOrGoalLead`), so the hook prints nothing for them. What they do that the lead would want to know, a status they set or a hand-over, is written to the news instead. The lead's own `crew set` isn't: it knows what it did.
- **What doesn't fit is left out, oldest first.** A hook's output is cut at 10,000 characters (`hookOutputCap`), so the news gets what's left after the hook's other line, and a first line says how many lines were left out and where to read them.
- **News is this machine's own**, like `logs/`: it isn't ledger, and isn't committed. After a lease moves, the new machine's leads hear only what happened there. `crew tick` removes day files and session records older than 30 days.

### Goals
The user hands the crew a goal, a list of items or a column on the project's tracker, and a **goal lead** works through it without them. The interactive lead stays the user's interface to everything, goal leads included.

```
you ⇄ lead: what the goal is for, where its items come from, what bounds it
  lead: crew goal new "<title>" → the user's words into the goal file's Goal → your go-ahead
        crew goal start GOAL
          ├─ detached checkout ~/agent-work/<p>/_goal-<id> at origin/<default> (plain git, like the gardener's)
          └─ claude --name crew-<p>-goal-<id> --add-dir <home> --bg --agent goal-lead
               --permission-mode <LEAD_PERMISSION_MODE> --settings "<lead settings without agent, env: project and home>" "<prompt>"
  goal lead, for every item, in one turn: crew new … --goal GOAL → intake to the brief standard
        → brief-reviewer → findings settled → crew ready TASK, or parked (draft, with Open questions)
  crew tick: dispatches the goal's ready tasks, highest priority first, as MAX_WORKERS / the goal's max_in_flight allow;
             resumes the goal lead (crew goal followup) with the user's notes, its workers' questions and its spikes' reports;
             closes the goal (crew goal done) once every task is finished
```

- **A goal is a ledger file**, `projects/<p>/goals/NNN-<slug>.md`, with flat front matter (`status`: `draft`, `running`, `done` or `abandoned`; the goal lead's `checkout`, `lead_name`, `lead_job`, `lead_session` and `lead_fingerprint`; `unsent_notes`; `max_in_flight`) and the sections Goal (the user's words, quoted, including where the items come from), Items (each one with its task, written by the goal lead), Decisions and Log. Like a task file, it is the goal lead's record, and the session can be replaced.
- **A task belongs to a goal through its `goal:` key**, set by `crew new --goal`. `crew status` lists each goal with its tasks under it, grouped by where they stand: in flight; next, numbered in the order `crew tick` dispatches them (`sortForDispatch`); waiting on other tasks, with `after <tasks>`; drafts with open questions, under `parked`; and the other drafts, under `planning`. A goal that isn't running lists its ready tasks under `ready`, unnumbered.
- **Parked is a task state, not a goal one.** The goal lead parks an item by leaving its task in `draft` with unchecked Open questions, so the rest of the goal carries on. The user answers through the lead, which records the answer in the task and passes it on with `crew goal note`.
- **The goal lead is told only what's new.** `crew goal note` records the user's words under the goal's Decisions and counts them in `unsent_notes`. A goal task's worker that asks something is found from its Open questions (not the `@login` lines `crew feedback` writes for collaborators); `questions_routed`, a checksum of the questions last sent, keeps one the goal lead left for the user from being sent again. A done spike's report is sent once too, with its answer and the draft it informs, and `report_sent` records it. `crew goal followup` sends all three, once the goal lead is free, and resets them.
- **The goal lead works one turn per input** and never polls (its prompt, and `disallowedTools` without `ScheduleWakeup` or cron). Every turn starts in a freshly fetched checkout. It doesn't count toward `MAX_WORKERS`, which caps workers: what it produces is capped where it reaches the user, by the goal's `max_in_flight`.
- **Dispatches wait, saying why.** `dispatchChecks` refuses with exit 4 (`notYet`) when a task only has to wait: a paused project (checked first), a goal or go-ahead that no longer lets tick dispatch it (with `--tick`, which tick passes, since either can change while the worktree is set up), a dependency that isn't merged or done yet (`pendingDeps`), a cap, or a stacked parent that hasn't pushed. It counts the caps only once the dependencies are through, since counting the workers running asks `claude agents`. `crew tick` leaves out paused projects' tasks, skips a task with pending dependencies without running `crew dispatch` for it, and holds back the rest of exit 4 with the reason `crew dispatch` gave (the last line it printed, after `crew: `); it tries them all again next tick, and the leads hear each reason (see [What the lead hears](#what-the-lead-hears)). Any other refusal is a warning.
- **`crew status` shows what holds dispatch back**, from the same `pendingDeps`, `workerSlots`, `goalSlots` and `sortForDispatch`, so the two agree on dependencies, caps and order. It counts the caps once for each project and goal, not for each task. A cap set to something that isn't a whole number shows as `?`, with the error on that project's or goal's line. Each note means one thing:
  - `after <tasks>`: the dependencies that haven't merged. An abandoned one is always named, `<task> (abandoned)`, since it never will. A stacked task's abandoned parent counts, whether it's in `depends_on` or only the `base`.
  - `on <parent>`: a ready task whose parent is in flight. It can go once the parent's branch is on origin, which status can't see. When the task's own parent has merged, the parent named is the first task down the stack that hasn't (`liveParent`), since that's where `crew dispatch` puts the task.
  - `full` on a goal's line: the goal is at its `max_in_flight`.
  - `full` on the `workers running` line: no project has a worker slot free. A project may set its own `MAX_WORKERS`, higher or lower, so each full project's line says `workers full` with its own limit.
  - `go-ahead once <task> is <status>`: a ready task outside a goal that `crew tick` dispatches once that task gets there, and `go-ahead met: <task> reached <status>` once it has: the next tick dispatches it, as its caps allow. `go-ahead never met: <task> abandoned`, with `dispatch by hand`, when the task it waits on was abandoned.
  - `dispatch by hand`: a ready task no running or draft goal, and no go-ahead, will dispatch. `goal <id> full` beside it means a done or abandoned goal's cap still holds it; a bad cap on that goal is said there too, since status doesn't list the goal.
  - `N to learn; <spike> <status>, …` on a draft: its open items still to learn, from its records, and the spikes that inform it. `informs <draft>` on a spike.
  - `N draft(s)`: drafts outside a goal with no open questions and nothing to learn, counted rather than listed.
  - `automated review off` on a task: the lead's choice at intake (`auto_review`). Its other choices, `model` and `effort`, have columns of their own.
  - `paused (crew resume --project <p>)` on a project's line: nothing dispatches for it, whatever its groups say, until it's resumed. `interrupted by a pause` on a task: the pause cut its worker's turn short, and `crew tick` tells it to carry on once the project is resumed.
  - Status lists a project's next tasks even when it isn't cloned here, though `crew tick` dispatches only projects cloned on its machine.
- **Ending a goal** (`crew goal done` or `abandon`) stops and removes the goal lead, any background process still running in its checkout, and the checkout, and leaves the tasks alone. A note to a done goal reopens it, for items added later. The ready tasks of an abandoned goal are the lead's to dispatch.
- **Items come from wherever the goal says.** If that's an external tracker, the goal lead reads it with the tools its session has and changes nothing there. How to reach a project's tracker belongs in that project's `AGENTS.md`, never in this repo.

### Gardener
`crew gardener [--all|--project P]` runs two agents over each project, one after the other. Each has a cursor of its own, so one failing doesn't hold back the other. It exits non-zero if any run fails.

1. Fetches the default branch and moves `_gardener` to `origin/<default>`. This checkout always uses plain `git worktree`, whatever `WORKTREE_TOOL` says: both agents only read, so they don't need the project's per-worktree setup.
2. **The gardener** (`reviewCommits`): sets the review range to `gardener.last..HEAD`. On the first run it starts from the commit before `GARDENER_LOOKBACK`. With no new commits, it starts no session.
3. **The misses agent** (`sortMisses`, `tasksToSort`): picks the project's merged tasks whose merge (the Log's, `mergedAt`) is after the time in `misses.last` and that have a comment of the user's after an automated review (`Task.CommentsAfterReview`). On the first run it starts from the date of the default branch's newest commit before `GARDENER_LOOKBACK`. A task merged in the current minute waits for the next run, so one synced later in that minute can't tie with the cursor. With no tasks, it starts no session.
4. Each runs `claude -p --add-dir <home> --agent <gardener|misses> --permission-mode acceptEdits --permission-prompts none --max-turns … --settings "<gardener settings, env: project and home>" "<prompt>"` (`runAgent`), writing its output to `logs/`. The misses agent's prompt lists the task files, and under each the comments to sort (`tasksToSort`), so the agent doesn't pick them again.
5. On success, each updates its cursor and commits (`advance`): `gardener.last` to the head it reviewed, `misses.last` to the newest merge time it read.

### Review eval
`crew review-eval [--project P] [--task T] [--limit N] [--rubric PATH]` reruns the reviewer on code automated review once passed, where the user then found something it missed, and reports which of those misses it finds now. The user runs it by hand after changing the rubric, the reviewer's prompt or its model. crew never starts it: each case costs a review.

1. **The test set** is derived from the ledger, never stored (`evalCases`). For each merged task, each comment the user made in a round after an automated review (`Task.CommentsAfterReview`) is a case, and so is each fix task naming it (`Task.Fixes`), unless abandoned, against the task's last review. A case's ID is the same in every run: `<task>/round-<n>/comment-<id>` (`review-<id>` for a review summary) or `<task>/fix-<fix task>`. A review whose `Range:` line crew can't read gives no case. `--task` keeps one task's cases (a task of the project `--project` names, when it's given), and `--limit N` the first N. A paused project's eval waits (exit 4), and a project runs one eval at a time (`.crew-eval-<p>.lock`): two would move each other's checkout. Before it starts each session, the run checks that the project isn't paused and that the rubric and the installed reviewer still have the hashes it started with (`evalRun.goOn`). If not, it stops for good: the remaining cases are `not run`, and the report says the run was cut short. The hashes catch `crew upgrade`, which replaces both, even when its pause starts and ends inside one review.
2. **Rerunning a review** (`evalRun.rerun`): `_eval` is a detached checkout (`detachedCheckout`), moved to the review's head. When the clone doesn't have that commit, crew fetches `refs/pull/<n>/head`: a squash-merged PR's commits aren't on the default branch. The range is always the whole PR as it was, `<fork point>..<reviewed head>`, also for a review that read only the commits since an earlier one. Cases on the same review share one rerun, since the reviewer gets the same briefing for each.
3. **The briefing** (`evalBriefing`) has the skill's first line and four headings (SKILL.md step 3), holding only what existed when the review ran: the Goal's quote, the `(user)` Decisions dated before the review's day (a decision has no time), the user's comments in rounds before the review, and the range's commits. The PR's text isn't recorded as it was then, so it's left out. Nothing later goes in: it could hold the miss itself.
4. The reviewer runs as `claude -p --agent reviewer --add-dir <run's log dir> --add-dir <rubric's dir> --permission-mode auto --permission-prompts none --settings config/readonly-settings.json "<SKILL.md step 4's prompt>"` in `_eval`: in auto mode, as it does under a worker, with the read-only `allow` list.
5. **The judge** (`judge`, `parseJudgement`) is `claude -p --tools "" --permission-prompts none "<prompt>"`, run in the temp directory, away from any repo's CLAUDE.md. Its prompt holds the miss (an inline comment after its place, ``On `a.go:3`: …``), the brief and what the user had said before the review (`briefBefore`: the Goal's objective and the task's Context, Acceptance criteria and Out of scope, with an older brief's Structure, Plan and Constraints, which the reviewer's briefing leaves out, then the briefing's request, decisions and comments) and the report, and asks for `found`, `missed` or `not a review finding` on the first line (the kinds in `notAFinding`, which are `agents/misses.md`'s not-a-miss items), then the finding that matches. The reviewer never sees the miss. A case whose rerun or judgement failed is `not run`, and counts in neither total.
6. **The report** goes to `projects/<p>/review-eval/<YYYY-MM-DD-HHMMSS>.md` and is committed (`evalRun.record`): what the run tested with (the rubric's and the installed reviewer's paths with a short hash of each, `claude --version`, and the `--task`/`--limit` that narrowed it, or `all`, then why it was cut short, if it was), the totals (found, of found and missed), a comparison with the project's newest earlier full run (`lastFullEval`: a narrowed run is a trial, and a cut-short run or one that judged nothing is partial, so neither is ever the baseline) on the cases both judged (`compareEvals`: now found, now missed, new cases, and which of the three changed), and a line per case. Totals alone wouldn't compare: the test set grows as tasks merge. What each session was given and said is in `logs/review-eval-<p>-<time>/`, which the report names.

### Proposals
A proposal is an idea worth keeping that isn't ready to be a task: a gardener refactor, a misses agent's fix at the source, or something the user, a lead or a worker wants written down. `crew status` shows only how many are open, so they don't look like work in progress.

- **One shape for every source.** Each is a file from `templates/proposal.md`. Its `source` says who wrote it: `gardener`, `misses`, `user`, `lead` or `worker:<task id>`. `revisit_when`, optional, is the condition that makes it worth acting on.
- **`crew propose "<title>" [--why TEXT] [--revisit-when TEXT] [--source S]`** writes one from a title and a paragraph (under Why it matters), with `source: lead` by default and the evidence sections left empty. A `worker:` source must name one task of the project; crew records its full ID.
- **`crew proposals [--any-status] [--all|--project P]`** lists the open ones, or all of them with `--any-status` (for P, the default project, or every project), with their source, and `revisit_when` on a line below. The lead runs it at intake and raises any whose title or `revisit_when` touches the task.
- **`crew promote`** turns an `open` or `deferred` proposal into a draft task. The task's Context names the proposal and who wrote it, its `revisit_when`, and whichever of Why it matters, Proposal and First step have text (`Proposal.TaskContext`).
- **An accepted proposal stays with its task.** `crew set` given a proposal's file runs the proposal's check (`Proposal.CheckSet`) and none of a task's: once it's `accepted` with a `task`, it refuses a new or empty `task` and any other status, so a promoted proposal can't quietly lose the task it became. `crew` can't tell a lead from a worker, so this catches mistakes rather than locking the file: the lead repairs a wrong link by editing the front matter by hand.

### Project memory
A project's memory is `projects/<p>/memory.md`: durable facts about the project that the user approved and every agent working on it should know, mostly settled domain decisions that outlive their task and private working facts collaborators shouldn't see. It isn't status, work, the repo's conventions (AGENTS.md) or the user's taste (`~/.claude/CLAUDE.md`). Claude Code's auto memory can't do this job: it's per repository, so the lead and brief-reviewer, which run outside every repo, never see it, and nobody reviews what goes in.

```
any agent: crew remember "<fact>" --why "<reason>" --source S
  → memory-suggestions.md: - [ ] **<fact>** <reason>. (<source>, <date>)   crew status counts it
lead ⇄ user: keep it? → the text after the checkbox, unchanged, into memory.md;
             the item ticked "→ kept" or "→ declined: <reason>"
session start, resume, clear, compaction: SessionStart hook → crew memory --hook
             → the memory of CREW_PROJECT, into the session's context
```

- **Agents suggest, the user approves.** Only the lead writes `memory.md`, on the user's say-so; `crew guard` blocks the worker and gardener roles from editing it. Everyone else suggests with `crew remember`, whose `--source` is checked by `ledgerSource`, as for proposals.
- **Every agent loads the whole file**, mechanically. A SessionStart hook with no matcher, in `lead/.claude/settings.json` (so goal leads too), `config/worker-settings.json` and `config/gardener-settings.json`, runs `crew memory --hook`, and Claude Code adds its stdout to the session's context. It runs again at every resume, clear, fork and compaction, so a session gets the memory as it is at that moment; a change made since reaches it at the next one. Launch-prompt lines would load only if the agent obeyed, and `--append-system-prompt-file` would keep a resumed session on its old copy.
- **The hook prints the memory of `CREW_PROJECT`**, after a line naming the file and the rule for weighing it (`memoryRule`, the only place that rule is written). It prints nothing for no project or `all`, so a lead started for every project, and brief-reviewer (a subagent gets no SessionStart), run `crew memory --project <p>` instead, as their prompts say. It always exits 0.
- **casual-observer gets none**, on purpose: its value is the read of a teammate who knows little. `crew observe` runs it with `readonly-settings.json`, which has no hooks, and without `CREW_PROJECT`.
- **The whole file is loaded**, and Claude Code passes on at most 10,000 characters of a hook's output, so the lead keeps `memory.md` under 9,000. Past the cap, Claude Code would replace the output with a 2,000-character preview and a file path, without asking the agent to read it, so `crew memory --hook` prints its header and an instruction to read the file instead (`hookOutputCap`). Loading an index and fetching entries on demand is the next step once a memory nears that.

### MCP servers for one project
A project's MCP servers, a tracker say, go in `projects/<p>/mcp.json`, the same shape as a repo's `.mcp.json`. A repo's `.mcp.json` doesn't fit: collaborators see it, and the lead, which doesn't run in the repo, never reads it. User scope doesn't either: it reaches every session in every project.

```
projects/<p>/mcp.json  (committed; a secret only as ${NAME}, a setting from the project's settings files, local.env for a secret)
  → projects/<p>/mcp.local.json   each server named <p>_<server>, ${NAME}s filled in
       → workers and goal leads of <p>: claude --mcp-config <it>   (rebuilt before every launch, resumes too)
  → lead/.mcp.json                every project's mcp.local.json servers
       → every lead, as the servers of its folder, approved by enableAllProjectMcpServers
       → a lead for Q: --settings {"disabledMcpjsonServers": [every server not in Q's mcp.local.json]}
```

- **crew fills in the values,** not Claude Code, so the rule is the same for every kind of session and no secret goes in a session's environment or on a command line. A value comes only from crew's settings, not the environment, so a worker the timer dispatches gets what one dispatched from your shell gets, as long as `local.env` holds the value itself: a `$VAR` in a settings file is still read from the environment.
- **Names are `<project>_<server>`** in both generated files. A project's name is `[a-z0-9-]`, so names can't clash between projects. A repo's own `.mcp.json` could still use such a name, which the prefix makes unlikely but doesn't prevent. One permission rule or `AGENTS.md` line works in every kind of session.
- **A resume takes no flags,** so a resumed worker keeps the `--mcp-config` path it started with. `launchSession` rebuilds the file first, so it's current. Every worker and goal lead starts with the path, whether or not its project has an `mcp.json` yet, so one added later reaches sessions already running. Generated files are never deleted: a project that drops its `mcp.json` gets one with no servers, which a resumed session can still load.
- **A lead for one project switches the others off** by exact name, from its own project's `mcp.local.json`, never by parsing names. It reads `lead/.mcp.json` as it is on disk, the file the session loads, so a server the last sync left there is switched off too. `claude remote-control` takes no `--mcp-config`, which is why leads get their servers from a file in `lead/`. The fallback, if `disabledMcpjsonServers` doesn't work as assumed, is a lead folder per project.
- **Keeping it current:** `crew tick` runs `crew mcp sync`. `crew install`, `crew lead` and `crew serve` call the same code, the lead commands before they start. Building one project's file, as a dispatch does, never reads another project's.
- **A broken `mcp.json`** stops its project's dispatches and followups before anything starts, with an error naming the file and the setting, and `crew doctor` reports it. `crew mcp sync` reports it and leaves that project's `mcp.local.json` as it was.

### Public and private repos
```
public crew repo (code, no state)
  └─ git clone → ~/crew; crew setup
       ├─ origin → upstream, its push URL DISABLED: a ledger can never reach the public repo
       ├─ gh repo create <login>/crew --private --source . --remote origin
       ├─ config/crew.env from templates/crew.env → commit → push
       └─ crew host up (below)
another machine of the person's: git clone <their private repo> ~/crew; crew host up [--take]
```

### Hosting and failover

**Claiming the lease** (`crew host up [--take]`):
1. `crew install`.
2. Pull, write this machine's name in `host`, commit, push. A rejected push means another machine moved first: drop the claim and look again. Without `--take`, a lease another machine holds is refused.
3. Clone each project this machine has no clone of into `$WORK_ROOT/<p>/repo`, and record it in `local.env`.
4. If `$WORK_ROOT` isn't trusted yet, open Claude Code there for the user to accept the trust dialog (`trustWorkRoot`), since workers' background sessions can't show it. crew catches Ctrl+C and hangup until `claude` exits, so leaving it any way goes on to step 5. Without a terminal, `crew doctor` says how.
5. Enable the services (`crewServices`: `crew-tick.timer`, `crew-gardener.timer` and `crew-lead.service`, or on a Mac the jobs `crew-tick`, `crew-gardener` and `crew-lead`), and run `crew doctor`.

**Holding it:** every change takes `lock`, which runs `requireHost`: `host` must name this machine, and `.crew-lease-lost` must not exist. Every ledger commit starts a background push (`pushSoon`).

**Losing it** (another machine ran `crew host up --take`):
1. This machine's next background push is rejected, finds origin's `host` names the other machine, and creates `.crew-lease-lost`. From then on this machine refuses every change.
2. Its next `crew tick` fetches, sees the same, and stands down: its `crew-*` sessions stopped, what origin lacks kept on a branch `lost/<host>-<time>`, the home reset to origin, and its services off. That removes `.crew-lease-lost`, as a later `crew host up` would. The services go off last, so a stand-down that fails on the way leaves the tick on, and the next tick tries again.

**Carrying on, on the new machine:** its `crew tick` gives a working task whose worker and worktree aren't there a fresh worker (`movedHere`, `crew followup --fresh`). `crew followup` and `crew restack` recreate a missing worktree from `origin/<branch>`, or start over from `origin/<base>` when the branch was never pushed.

**Handing over on purpose** (`crew host down [--force]`): refused while a task worktree has unpushed commits; then the services off, sessions stopped, the ledger pushed, and an empty `host` pushed. `crew host up` on the next machine needs no `--take`.


- **Losing a machine loses little:** the ledger is pushed seconds after each change, and workers push their branch after every commit. Session transcripts stay on the old machine, which is why a moved task gets a fresh worker: principle 3 already lets any worker be replaced.
- **The phone follows the lease:** `crew-lead.service` runs only where `crew serve` finds the lease (it exits 3 elsewhere), so Claude Mobile's `crew` is always the machine that runs the crew. On a Mac, launchd can't leave the job stopped on exit 3, so it's started again every 30 seconds, exiting 3 at once, until the next tick there stands the machine down and boots it out.

### Pausing
```
crew pause [--project P|--all] [--force]
  lock → projects/<p>/paused (by: crew pause, at, host), unless a pause other than crew upgrade's is there
       → busySessions: the projects' workers and goal leads mid-turn → interrupted: <time> on the file of each
         whose task or goal isn't finished
       → commit → unlock
  wrap-up: up to WRAP_UP_SECONDS (180, one tick), polling claude agents; then, under the lock, claude stop
           on any still mid-turn whose project is still paused, logged "stopped by crew pause before it ended
           its turn". Idle sessions are left as they are. A session that won't stop is named, and the pause exits 1
  --force: claude stop on every open worker and goal lead the projects' files record, busy or idle, finished
           or not, logged "stopped by crew pause --force"; then ends what closed ones left running in the
           background in their worktrees and checkouts (endBackgroundWork)
  every stop also ends the background processes in the session's worktree or checkout (stopProcessesIn), and
  sets interrupted on its file unless its task or goal is finished
  each worker's and goal lead's PostToolUse hook, crew pause --hook: CREW_PROJECT is paused → "record where you are, end your turn",
  and interrupted on the session's own file (markInterrupted, by the session_id on its input)
crew resume [--project P|--all]
  lock → remove the marks → commit; the next crew tick follows up each file with interrupted
```

- **The mark is in the ledger**, so it's committed, pushed, and holds on whichever machine runs the crew. `Project.Paused` and `Project.PausedBy` are the only readers. `by` is for code to read: a pause leaves another's mark alone, except one `crew upgrade` wrote, and the upgrade lifts only a mark it wrote, so the user's pause outlasts an upgrade.
- **Nothing starts a session for a paused project.** `crew dispatch` (once it takes the lock, and in `dispatchChecks`), `crew followup`, `crew restack`, `crew nudge`, `crew goal start` and `crew goal followup` refuse with exit 4 (`refuseIfPaused`), before their first side effect and again under the ledger lock, so a pause written in between holds. `launchSession` doesn't check: it runs after its callers' side effects, too late to hold them back. `crew gardener` skips the project. `crew review-eval` refuses with exit 4 before it starts, and checks again before each session it starts. The user's interactive leads are untouched.
- **Interrupted work carries on.** `interrupted` is set before the wait, so a pause cut short (Ctrl-C, a Bash timeout) still records it. A session the pause stops gets it too, busy or idle: an idle one may have been waiting on a background review, which the stop ends. `crew followup` and `crew goal followup` deliver it ("crew was paused while you were working…", `carryOn`) and clear it once the session has started, the way `crew followup` owns `last_round_sent`. `crew tick` only reads it. A session started before its settings had the hook starts fresh (its fingerprint changed) and rebuilds from its file.
- **The hook is added by `addPauseHook`**, not listed in a settings file, so only workers and goal leads get it. A lead running `crew pause` would otherwise be told to stop itself. The gardener doesn't get it either: it has no file to note where it stopped, and `crew gardener` would take an early end for a finished review and move `gardener.last` past what it didn't read. A gardener run that started before the pause runs to its end. Until the project is paused, the hook reads only `CREW_PROJECT` and the mark, since it runs after every tool call. Once it is, the hook also finds its session's file by the `session_id` on its input and marks it interrupted, once: a session idle when the pause began can start a turn later, when a background review reports back, and nothing else would record that it was cut short.
- **The wait holds no lock**, so workers can `crew log` where they stopped while it runs. The stop holds it, and stops only the sessions whose project is still paused, so a `crew resume` during the wait lets them go on, and no followup can start one between the check and the stop. `stopJobs` stops them together, with one 10-second wait, and `stopProcessesIn` then ends their background processes with one more, to keep that hold short.
- **A failed `claude agents` is never read as nothing running** (`listAgents`, where `agents` gives an empty list): the pause fails before it writes anything, a failed poll in the wait counts for nothing, and a job counts as stopped only once it's listed closed or not at all.

### Upgrading
```
crew upgrade [--yes]
               .crew-upgrade.lock, held to the end; a second upgrade refuses at once
               → lock (the host only) → refuse a dirty home
               → the newest v<version> tag upstream has (git ls-remote --tags upstream) → unlock
               → CREW_VERSION=<version> bin/crew version: the launcher downloads that release's binary;
                 if it can't (the release may still be building), refuse, with nothing changed
               → confirmUpgrade: the versions, the sessions mid-turn (busySessions), what happens to them;
                 then the y/N prompt on a terminal, or --yes; without either, refuse, with nothing changed
               → unless HEAD has the tag already (a run that stopped after its merge), pauseAndMerge:
                 pause every project, by: crew upgrade (see Pausing): the wait holds no lock
                 → lock → refuse a dirty home or a newer tag → git fetch upstream tag v<version>
                   → stillPaused: refuse a project resumed or added during the wait, or a session mid-turn
                     (one that woke during it)
                 → git merge --no-edit v<version> → unlock
                 a refusal lifts this run's marks, not an earlier run's; a conflict (only the person's own edits to crew's files can
                 conflict) stops with the merge left in progress, the crew still paused
               → the new version's bin/crew install (--yes with --yes); a failure stops, the crew still paused
               → resume the projects whose mark says crew upgrade
               → push → restartLeadService (systemctl restart, launchctl kickstart -k)
               → remove the other versions' binaries from bin/release/
```

- **The upgrade pauses the crew**, so no worker or goal lead is mid-turn when the release is merged. A session that wakes during the install isn't caught: the install takes seconds. It's what `crew upgrade` always does, behind a yes: the user chose a confirmation over an option to wrap up or a refusal while sessions work. A lead runs it once without `--yes` to get the text to show the user, then again with `--yes` on their go-ahead.
- **The upgrade knows its pause by the mark**, not by memory: it lifts every mark whose `by` is `crew upgrade`, so a run cut short (Ctrl-C, a closed terminal, a lead's Bash timeout) leaves marks the next one lifts. A project the user paused keeps its own mark. A failure before the merge lifts the pause it made, but not marks an earlier run left, whose release may be merged and not installed. Once the merge has begun, the crew stays paused until the release is installed and the ledger migrated (`runNewVersion` runs the new version's `crew install`, then its `crew migrate`): after a conflict git takes no ledger commit until the merge is settled, and after a failed install the sessions would resume on a half-installed release. `crew upgrade` run again then finds the tag in HEAD, so it pauses nothing, installs, and lifts the marks.

A session keeps the agent file and settings it started with, so after an upgrade:

- **Workers and goal leads** start fresh, not resumed, the next time crew has something for them, when their instructions or settings changed (`<prefix>_fingerprint`, see `relaunch`), or a worker's model or effort did (`worker_model`, `worker_effort`). They rebuild from their task or goal file. One whose didn't change keeps its conversation.
- **A cold worker with a big context starts fresh too** (`coldResume`, in `followup`). Its prompt cache lasts an hour after its last request, so resuming it later writes the whole context to the cache again. Once that context reaches 100k tokens, a fresh worker rebuilding from the task file costs less: on this machine's workers in November 2026, it did in 61 of 70 such rounds, and lost below 100k. crew reads the last request from the session's transcript, by its reply's timestamp rather than the file's, since a session writes other entries after it, and leaves out its subagents' requests, which keep no cache of the session's. A transcript that can't say, because there's none, it holds no request, or a line in it doesn't read (a reply cut off as it was written, say), resumes as before. Goal leads always resume: they don't go through `followup`.
- **Interactive leads** are the user's sessions, so crew never restarts them. `crew lead` puts `leadFingerprint` in the session's environment as `CREW_LEAD_FINGERPRINT`, and the lead's UserPromptSubmit hook, `crew lead --hook`, prints a line once it differs from the current one, which Claude Code adds to the prompt. The lead tells the user to start a new `lead`. `claude` strips the variable, and `sessionSettings` sets it empty, since a background session takes the environment of whatever started Claude Code's daemon (a lead's own `claude agents`, say). So goal leads, which share the lead's settings, never hear it, and nor does the phone lead, which `crew serve` starts through `claude`.

A home moves only from release to release, so its agent prompts and its binary always come from the same one. Releases are made in the public repo: pushing the tag `v<version>` (it must match `VERSION`) runs `.github/workflows/release.yml`, which runs the tests, and `go test` on `macos-latest`, builds `crew-Linux-x86_64`, `crew-Linux-aarch64`, `crew-Darwin-arm64` and `crew-Darwin-x86_64` with the version stamped in, and publishes them as the tag's release only once both pass, titled `crew <version>`, the tag's message as its notes. It refuses a lightweight tag, for which `gh` would publish the commit's message instead. The workflow runs only in the public repo, so a private home that pushes a tag builds nothing.

## `crew` internals (`cmd/crew/`)

Go, in one package, on the standard library and, for `crew status`'s live view only, Charm's bubbletea and lipgloss. Each area has a file of its own; each command is a `cmd…` function in a `cmd_*.go` file.

- **The launcher (`bin/crew`):** a POSIX `sh` script, the only `crew` on `PATH`. It finds itself through symlinks, reads `VERSION` from its own checkout (or takes `CREW_VERSION` from the environment), and runs `bin/release/crew-<version>` with `CREW_HOME` set to that checkout, unless it's set already.
  - A missing binary is downloaded once with `curl` from the public repo's release `v<version>` (`crew-<uname -s>-<uname -m>`), to a temporary file that is run with `version` to check it, then renamed into place. `bin/release/` is gitignored, so a fresh clone works on a machine without Go.
  - When it can't get a binary, it says why and exits 1, or 2 when called as `crew guard`, so a missing binary blocks edits.
  - The release URL is written into it; a fork changes that one line.
- **Home and config (`home.go`, `env.go`):**
  - `CREW_HOME`, exported, so the hooks, `wt` runs and foreground sessions crew starts see it. A background session gets it from its settings (`sessionSettings`).
  - The settings are `config/defaults.env`, which sets every key, then `config/crew.env` if it exists. `projectSettings` adds `projects/<p>/project.env` (committed: `REMOTE`, `DEFAULT_BRANCH`, overrides), then `projects/<p>/local.env` (this machine's `REPO`, gitignored), starting from the shared settings for each project, so one project's values never reach the next. `ledgerProject` builds a project on it, cloned here or not, for `crew pause` and `crew resume`, which need only the ledger; `loadProject` builds on that, and fails when this machine has no clone. `crew mcp sync` needs no clone either, so it reads only the settings.
  - The settings files are shell-style but parsed, not sourced. A line is blank, a `#` comment, or `KEY=value`, where the value is one shell word: plain, `'single-quoted'` and `"double-quoted"` parts, with `$VAR` and `${VAR}` taken from the settings read so far or the environment, then an optional `# comment`. Anything else, a command substitution or an unset variable say, is an error naming the file and line.
  - `crew config [KEY] [--project P]` prints the effective value, for P or the default project. `--task T` gives T's worker's: its project's, with `AUTO_REVIEWS` as the task's `auto_review` sets it.
- **Project scope (`home.go`):** a command works on the project `--project` names, else the default project (`defaultProject`): `CREW_PROJECT` when it's set, else the project whose repo the current directory is in. `--project all`, `--all` or `CREW_PROJECT=all` is every project, and so is no project at all for the commands that list (`scope`). Commands that write to one project fail without one (`oneProject`).
  - `CREW_PROJECT` wins over the current directory because a session's directory is only wherever its shell last went: a lead reading code in `_lead` is still the lead it was started as.
  - Every session crew starts has it: a worker, goal lead or gardener has its project in its `--settings` env (`sessionSettings`, below), and the Remote Control lead has `all` from `crew serve`'s environment. `crew lead` sets it to `--project P`, the project whose repo you ran it in, or `all`. So the current directory scopes only your own shell.
- **Errors (`main.go`):** a command returns its refusal as an error: `fail` (exit 1), `notYet` (exit 4) or `exitQuietly(code)` for one that has said what it had to (`crew feedback`'s, `crew ci-fix`'s and `crew catch-up`'s 3 for "nothing new"). `main` prints the message as `crew: …`. `warn` reports what doesn't stop the command.
- **Operations (`operation.go`):** code inside a long-lived crew process, such as `crew status`'s live view, calls a command's work directly, rather than running `crew` as a child and reading what it prints. A command callable this way is an *operation*:
  - Its `cmd…` function only reads the command line and calls it. The operation does the work and returns what happened as a value, with a refusal as its error.
  - Everything on its path reports through its `Crew`: `c.warn` for what doesn't stop it, and `c.printf` or `c.out()` for what it's doing. From a shell, these go to the terminal as `warn` and `fmt.Printf` do.
  - `runInProcess` runs it on a `Crew` of its own, which writes nothing to the terminal and hands its warnings back. It reads `config/crew.env` again, as a `crew` process would, so a change made while the long-lived process runs counts. That `Crew` takes `.crew.lock` with a file of its own and lets go of it when the operation returns, so the calling process holds no lock between calls, and two operations in it wait for each other as two processes do.
  - An outcome that is neither done nor refused has an error type of its own, so the caller tells it apart with `errors.As`, never by reading the text.
  - A question the caller asks before acting, such as whether a note would be sent, is a method that gives the operation's own refusal, from the check the operation makes.

  `followup` is the first operation. It returns `followupSent`: the worker, how it was reached, and how a missing worktree came back. It refuses through `followupRefusal`, which `noteRefusal` asks before the user writes a note. It ends in `unrecordedSession` when claude started a session crew couldn't record, and in `worktreeError` when the task's worktree couldn't be brought to this machine. `crew review`, `crew dispatch` and `crew tick` become operations the same way when the live view needs them; `crew tick` still runs each of its steps as a process of its own.
- **Locks (`lock.go`):** `flock(2)` on files in the home, the same lock util-linux `flock` takes. `lock` takes `.crew.lock` (30 s timeout) for the rest of the process, or until `unlock`, and then checks the lease (`requireHost`). `takeLock` is the lock alone, for the commands that move the lease. `.crew-tick.lock` lets one `crew tick` run at a time, `.crew-push.lock` one ledger push, `.crew-evidence-<p>.lock` one `crew evidence` for project p, `.crew-news.lock` one writer or reader of the news (`lockNews`), and `.crew-upgrade.lock` one `crew upgrade`, since it lets go of `.crew.lock` while sessions wrap up. Go opens files close-on-exec, so the sessions and processes crew starts never hold a lock. `crew dispatch` unlocks while it creates the worktree, since Worktrunk hooks can take minutes and workers' `crew log` calls would otherwise time out; it repeats its checks once it has the lock again.
- **Codex (`cmd_codex.go`):** `crew codex` is the only way crew runs Codex, for `pr-review`, in a new session each time: a rebuttal round starts Codex fresh with a round file, as it does the Claude reviewer, so there's no thread to keep. - **Status (`status_report.go`, `cmd_status.go`, `status_table.go`, `status_live.go`):** `crew status` works out everything it shows before it prints anything. `buildReport` (`status_report.go`) builds a `statusReport`: every project, the ones in scope in full (their goals, each goal's groups by `groupKind`, and rows, each with its `Task`, worker, notes and the rows stacked on it) and the rest only as what waits on the user (`waitingOnUser`). It prints nothing. Each `pr-open` row carries a `mergeCheck` (`merge_check.go`): "merge now", or "not yet:" and what stands in the way, the blockers likeliest to clear soonest first. It is judged from the PR as GitHub last answered: before building the report, `readPRs` asks for every pr-open PR in the projects in scope at once, through the same `readPR` crew sync records from (`github_pr.go`), and keeps each answer or error by project and by the PR as its task names it, since two projects' repositories can each have a PR 12. The workers and the branches are read the same way, before the build: `listWorkers` keeps what `claude agents` listed, or why it couldn't, and `readBranches` keeps each in-flight task's restack and retarget reasons, which run git only for a stacked task or one whose PR is off its base. `buildReport` takes the three as one `statusReads` and runs nothing itself, no `gh`, `claude` or `git`, so a report can be built again from the same reads. A read the report wasn't given yet is said as such, never taken for an empty one: the workers line and each worker say `not listed yet`, a task in flight that git is asked about notes `branches not read yet`, and either keeps a pr-open row from `merge now`. A branch read holds for the task's place in its stack when it was taken (`stackPlace`: its base, and its parent's status), so a parent that merges since makes it not read again. A PR GitHub didn't answer for falls back to what sync last recorded (`syncedPR`), and the check says so; one that wasn't asked for says `PR not read on GitHub yet`. Status writes none of it to the ledger. The merge check takes over the notes that say the same thing on a pr-open row: its `(pr_state)`, restack, retarget and open questions. `reportLines` (`cmd_status.go`) turns that report into a tree of lines, and only it words them, names a group's heading, marks what's folded (drafts with nothing to ask, a running goal's next tasks after the fifth) and puts each line under the one it belongs to: a task under its goal's group, a stacked task under its parent. Each line has a key, named from the facts it shows, that stays the same from one report to the next. A task's or a goal's line carries its fields (status, worker, PR, model, effort and notes), which `status_table.go` lays out as a table under named headings. `measure` makes each column as wide as its widest value across the lines it's given. `printReport` prints the tree as plain text, in that table, with each folded line's kids left out (`asPrinted`) before it measures, so a column is as wide as what's printed in it. In a terminal, `crew status` shows the same tree live instead (`status_live.go`), so it can't group, stack or word tasks differently from the text. It fits the table to the terminal (`fit`): each column up to a cap, a longer value wrapping inside its column, so a row can take several lines. The live view measures the whole tree, folded lines included, so opening one never moves the columns. The cursor moves by whole rows, and the screen scrolls by screen lines: ↑↓ scroll through a row taller than the screen before moving on, and the page keys move a screenful of lines. Where even the caps don't fit, each row is a card (`card`): its ID, then a line per field. The view keeps the cursor on the same line by its key, and runs five jobs from its `statusFeed`, each in the background and on its own, so one that hangs holds back neither the others nor the keys: it builds the report every 3 seconds, from its latest reads, lists the workers and reads the branches every 15 seconds, reads GitHub every 30 seconds and, on a machine that doesn't run the crew, pulls the ledger every minute. A beat each second starts whichever is due and not already running, and a read that comes back asks for a build at once. So a change to the ledger shows within 3 seconds, a worker's state or a restack within 15, and `r` asks for every read at once. `--plain` pulls, reads and builds once, which is what a plain `crew status` always did.
- **Stats (`cmd_stats.go`):** `crew stats` only reads: no lock, no commit, no `requireHost`. `statsOf` measures one task (`taskStats`) from what `ledger.go` reads and the project's `history`, and `cmdStats` picks the tasks merged since the date and prints them. A PR's wait runs from `status → pr-open` to the next change of status (`waited`). A question's runs from `status → needs-input` until the task leaves `needs-input` or merges; in a goal's task it starts instead at the goal lead's `For the user:` line, or at a line ending `recorded under Open questions for the user` (`recordedForTheUser`). A task dispatched before `Task.SetStatus` (its `dispatched` line has no status line just before it) first gets the status lines its dispatch, followup and `PR merged` lines stand for (`withStatusLines`), until 2026-12-31.
  - **Later fixes and reverts:** `historyOf` builds a project's `history` once: a `correction` for each merged fix task, traced by its `fixes`, and for each revert on `origin/<DEFAULT_BRANCH>`, traced by the PR whose merge or squash commit it reverts to the task whose `pr` is that PR. The reverts come from one `git log` of the whole branch in the project's clone, after a quiet fetch, since a revert names the reverted commit only by its SHA (`revertedPRs`, a pure function). Without the clone, with a shallow one, or when git fails, `history.unchecked` says why and the report goes on. `statsOf` counts a task's own corrections, whenever they came; the report lists those made since the date, whenever their cause merged, so a fix weeks after its cause still shows. Tasks and corrections are grouped by their tier with `byTier`, and the table lists the tiers in `risks` order, then no tier.
- **Costs (`cmd_costs.go`):** `crew costs` only reads, like `crew stats`, and covers every project: what this machine's transcripts say each step cost from a first day to a last, at the API rates in `apiRates` (dated `ratesDate`). `scanTranscripts` charges each API message once, by its ID (`messages`, shared with `crew review-cost`), to a step. A transcript folder's step, and its task for a task's worktree, come from the ledger (`transcriptOwners`): the lead's, each project's gardener checkout (where the misses agent runs too), its `_eval` checkout, each goal's checkout, each task's worktree, and anything else is "Other Claude Code sessions". A subagent in a task's worktree is charged to its own step (`subagentStep`): the agents `/simplify` and `/security-review` start (`skillRun`, which takes the Agent calls straight after the skill's Skill call; a skill that starts none leaves its window open, so the worker's next built-in agent is charged to it), `casual-observer` and `reviewer`, or else a step named by its agent. A brief review is its own step, wherever it ran, charged to the task whose file its first prompt names (`briefTask`), and a lead's or goal lead's other agents are charged to a step for them (`leadAgentSteps`). `costsIn` totals what was sent in the range; the transcripts are complete from when the oldest session Claude Code deletes by age, one run only from the command line, was last written (`completeFrom`, from the session's own transcript, not its subagents'), and the report says so when the range starts earlier. A model with no rate is reported with the tokens sent in the range, not priced. A step's median per task is over the tasks that merged or were done in the range (`finishedAt`) and ran it, each counting all it spent, whenever sent. It counts only tasks the transcripts hold whole (`wholeTasks`): one begun (`created`) before `completeFrom` may have lost sessions to age, and one under way while another machine held the lease (`tenuresElsewhere`, from the `host` file's history) has sessions on that machine (its finish is a Log time with no zone, on the clock of whichever machine held the lease, so against each other machine's tenure it's read on both clocks and the later counts: `latestFinish`), so both are left out and counted, as is a task with a message at a model with no rate, or with nothing spent in the transcripts. Any other way spend goes missing, such as a brief review a lead ran off the host, it can't see.

- **Lease (`lease.go`, `cmd_host.go`):** one machine runs the crew at a time, the one the home's `host` file names (`CREW_HOST`, from the environment, default `machineName()`: the short hostname on Linux, `scutil --get LocalHostName` on a Mac, since a Mac's hostname can change with the network).

Reads work anywhere, and `crew status` on another machine pulls first and says it's read-only.

Pushes take turns on `.crew-push.lock`: a push that finds one running leaves the work to it, and the running one checks again after it lets go of the lock, so a commit made while it held the lock still goes out.

A push rejected because origin has commits this machine lacks fetches them and rebases the ledger onto them (`git pull --rebase --autostash`) under the ledger lock (`adoptOriginCommits`); a rebase that conflicts is aborted and left for the next try.

- **Ledger files (`ledger.go`):**
  - A `Doc` is a task, goal or proposal file. It reads the file afresh for every value and writes it back at once, under the ledger lock: agents edit these files too, so nothing is kept in memory. `Task`, `Goal` and `Proposal` wrap one with the keys each has. `Status` and `GoalStatus` are the statuses, and `kinds` the kinds of task with what each asks; a Go test checks each list against `LEDGER.md`.

  - `Section` returns a section's text without HTML comments or blank lines; `crew ready` uses it. `crew hand-over` reads the criteria with it (`Task.AcceptanceCriteria`), which of them are the user's to check (`Task.UserChecks`) and the evidence (`Task.Evidence`, and the PR body's with `PREvidence`), and `crew ready` checks each criterion is a `- ` item. `InsertBefore` puts review rounds before `## Log`.
  - `Log` appends to the end of the file, so **`## Log` must stay the last section**. `LogEntries` reads the lines back as written, not through `Section`, so a message that quotes `<!--` doesn't hide the lines after it. `Task.SetStatus` is the only writer of a task's status, and logs each change as `status → <status>`.
  - `Task.AutomatedReviews` reads the record under `## Automated reviews`: each review's findings, their outcomes bucketed by first words (`Finding.Outcome`), and whether it was clean (`AutomatedReview.Clean`). `Task.ReviewRounds` reads each round's number, time and comment items; `Task.ReviewComments` counts the items, and `Task.CommentsAfterReview` pairs each item in a round recorded after an automated review with the newest review before it, from the headings' times.
- **Records (`records.go`, `cmd_learn.go`, `cmd_migrate.go`):** typed facts about a ledger file, in its records file beside it (`Doc.RecordsPath`: `tasks/<id>.records.jsonl`), which crew decides from instead of the file's prose. A `Record` has an `id`, `at`, `by` (the command that wrote it) and exactly one payload: `to_learn` or `learned`.
  - Only crew commands write them, through `Doc.AddRecords`, which adds a command's records after the file's others in one write, under the ledger lock, then `commit`. Like every write of a ledger file (`replaceFile`), it writes a temporary file and renames it over the old one, so a write that fails partway leaves the old file whole. None is ever changed; a later fact is a new record that names the one it follows. The guard refuses Edit and Write on a records file and on `ledger-format`, for every role.
  - `Doc.Records` reads strictly: an unknown field, a second value, a payload missing what it needs, a repeated ID or a `learned` record whose item no line adds fails the read, naming the file and line. Every reader passes the failure on rather than counting what it could read: `crew ready` refuses, and `crew status` shows it on the task's row.
  - Two clones that each add records merge without a conflict (`.gitattributes`: `merge=union`), and since nothing is rewritten, the union is every record from both. Both may settle one item: `LearnItem.Answers` keeps every answer.
  - `ledger-format` holds the format the project's ledger is in. `Doc.Records` fails unless it's `ledgerFormat`, saying to run `crew migrate` for an older one and `crew upgrade` for a newer one, so a home that upgraded but didn't migrate never reads its records as empty. `crew project add` writes it for a new project; `crew migrate` brings each project up to it once (format 1: `checkboxes` moves still-to-learn checkboxes into records), and `crew upgrade` runs the new version's `crew migrate` while the crew is paused. `crew doctor` names a project not in the format. A migration writes each task's records in one go before it changes the task file, so a run cut short is safe to run again: a task with records `crew migrate` wrote is only tidied.
  - `Task.StillToLearn` is the task's items, from `to_learn` and `learned` records alone. `crew to-learn` adds one to a draft and `crew learned` settles an open one, refusing an unknown or settled ID. Neither touches the task file: `crew show` (`shownTask`) renders the items, with when each was added and settled and its answers, under `## Still to learn`, and sets apart any line typed into that section as not an item.

- **Resolution (`resolve.go`):** `resolve` accepts:
  - a path;
  - `#<pr>` (matches the `pr` field);
  - an exact ID;
  - a number (`7` → `007-*`);
  - a unique substring.

  It searches the default project first (see Project scope), then all projects, so a task number or ID two projects share resolves in a scoped session. Every project numbers its own tasks, so even an exact ID can match in two. On ambiguity it prints the candidates, each with its project, and fails.

  `crew show` and `crew path` name a file by a type word, then its argument (`showKinds`, `ledgerFile`). `task`, `proposal` and `goal` go through `resolve`. `memory` and `memory-suggestions` are that file of the project `crew memory` would pick (`oneProject`). `file` goes through `resolveFile`, which looks only directly inside the home's `reports/`, `logs/` and `news/*.log`, and a project's `review-eval/` (`freeFiles`), the default project first, as `resolve` does. It matches by name (`resolveName`): a whole name, with or without its extension, before a part of one. With no type word, the argument is a task.

  `taskArg` names a task for a command to paste, as `crew attach`'s hints do: by its ID when that resolves back to it from here, else by its path.
- **Sessions (`sessions.go`):**
  - `agents` returns what `claude agents --json --all` lists as `Agent`s, or nothing on failure. It reads each field on its own, so a field whose type changes loses only that field. It sets `TurnEnded` on a `working` session whose transcript (`transcript`: `~/.claude/projects/*/<session>.jsonl`) ends with the `turn_duration` entry Claude Code writes when a turn ends (`turnEnded`), whether its process is still running or not. `quietFor` is how long ago the transcript last changed.
  - `busy` counts a job as busy while a turn runs (`state` working) or while its live process holds an open prompt, such as a permission request (`status` waiting). A `blocked` job without an open prompt ended its turn on a question for the user, so it takes a followup: the answer is what the followup sends. A background shell the worker started, such as a dev server, keeps its `state` working and its `status` busy after its turn ends, so a `working` job counts as mid-turn only until it has `TurnEnded`. `jobState` shows such a job as "idle, background task running". `runningWorkers` and `closeSession` use the same rule.
  - `runningWorkers` counts the busy sessions whose job a task file records as `worker_job`, across all projects. It doesn't go by name: a session Claude Code copies on resume gets a name of its own.
  - `stopJob` runs `claude stop` and waits up to 10 seconds for the job's `pid` to clear. `closeSession` uses it on a recorded session that isn't busy but whose process is still open, before a resume or a fresh session in its place, and returns the job whose process stays open: busy, or not closing.
  - `removeSession` stops a listed job whose process is open, busy or not, then runs `claude rm` on it. It fails only if the process won't close.
  - A `launcher` is what a kind of session starts with: its project, the prefix of its keys in the ledger file (`worker`, `lead`) and its launch flags. `launchWorker` and `launchGoalLead` build one, and are the only places a worker's or a goal lead's launch flags are chosen; `launchSession` builds the command line around them.
  - `launchSession` starts or resumes, with a launcher, the background session a ledger file records (`<prefix>_name`, `<prefix>_session`) and confirms it started (`waitForLaunch`). It strips color codes from `claude`'s output before reading the job ID, and fails rather than record an ID that doesn't look like one (`unrecordedSession`). A resume passes only the session and the prompt. `relaunch` falls back to a fresh session when a resume didn't start one (`notStarted`, which says why, with what `claude` said). Neither writes the ledger: their callers record the `launch` they return with `launch.record`, the only place `<prefix>_job`, `<prefix>_session`, `<prefix>_fingerprint` and `<prefix>_model` are set. Before either, `launchSession` stops the recorded session's process if it's open and idle (`closeSession`). If the process stays open, or is busy, it sends nothing and fails, naming the job and saying to stop it in `claude agents` and try again: resuming would start a copy, and a fresh session would work beside it in the same directory. That holds for every fresh start in a recorded session's place: `--fresh`, a changed launcher (`changedSince`), a cold worker (`coldResume`), the worker after a restack, and the restack session itself. That isn't `notStarted`, so `relaunch` starts no fresh session either, and input the ledger keeps (a round, goal notes) waits for a later `crew tick`. `waitForLaunch` waits until a resumed process has taken its prompt, so the next command finds it busy ("Resuming a background session"). Once a fresh session has started, it takes the one it replaces out of agent view (`removeSession`), unless that one is busy, so an upgrade that starts every worker fresh doesn't leave a stopped copy of each behind.
  - A launcher's `fingerprint` is a short hash (12 hex characters of SHA-256) of what its fresh session loads: its launch flags, settings included, but not its name or MCP config paths, and its agent files (`agentFiles`): the role's own, and every file in `agents/` that isn't a role of its own (`sessionRoles`), since which subagents a role runs is said only in its prose. A goal lead's also include `lead.md`, whose intake it follows. It reads their installed copies in `~/.claude/agents/` (`installedAgents`), which are what Claude Code loads, so a session started while `crew upgrade` has merged a release but not yet installed it records what it really loaded. Skills are left out: a session loads them from the home each time. `record` writes it on a fresh start only. A restack session's also takes in `restackPrompt`, which tells it to run the restack and nothing else (`launchRestack`), and `followup` starts a fresh worker after a session with that fingerprint. Otherwise `relaunch` is the one place it's compared: a recorded fingerprint that isn't the launcher's, or none, makes a would-be resume a fresh start, with the reason in the launch's `mode`. A resumed session runs on what it started with, so this is how a release's new instructions and settings reach workers and goal leads, while a release that changes neither keeps their conversations.
  - A worker's launcher also has a `model` and an `effort`: its task's, or none for Claude Code's defaults, and `restackModel` with no effort for a restack. A fresh session gets them as `--model` and `--effort`, and `record` writes them as `worker_model` and `worker_effort`. They stay out of the fingerprint, so an unset one launches as before, and `relaunch` compares each on its own (`changedSince`), so the reason for a fresh start says which changed: the model, the effort, the instructions or settings, or any of them.
  - A fresh worker gets `--agent`, `--permission-mode`, `--add-dir`, `--autocompact` (`WORKER_AUTOCOMPACT_WINDOW`, 400k by default, so a worker carried through several review rounds compacts long before its 1M window fills) and `workerSettings`: `config/worker-settings.json`, merged with `projects/<p>/worker-settings.json` when it exists, then `leanSettings`, and with the session's env (`sessionSettings`), as a JSON string. The merge is add-only (`addOnly` in `json.go`): objects merge, arrays append new entries, and any value the base sets wins, so a project can add `allow` rules or `env` but can't drop a `deny` rule.
  - `launchSession` starts with `refreshMCPConfig`, before a fresh start and a resume alike: it rebuilds the project's `mcp.local.json`, and gives every fresh session `--mcp-config <file>`, empty while the project has no `mcp.json`, so servers added later reach it on its next resume. `--mcp-config` is variadic, so it goes first, never right before the prompt.
- **JSON (`json.go`):** the settings crew writes keep their keys in the order their files have them, as jq's output did: the user's `~/.claude/settings.json`, merged worker settings, and a goal lead's settings.
- **Stacks (`stacks.go`):** `Branches` indexes a project's task files by branch, and `parentOf`, `effectiveBase`, `restackReason`, `retargetReason`, `onBase` and `noteBaseSHA` build on it (see [Stacked tasks](#stacked-tasks)). They read git only through `REPO`, whose refs the task worktrees share, and never touch its working tree.
- **Goals (`cmd_goal.go`):** `goalTasks` finds a goal's tasks by their `goal` key; `goalFinished`, `workerQuestions` and `unroutedQuestions` build on it. `questions_routed` is a POSIX `cksum` of the questions (`cksum`), so ledgers the bash crew wrote keep working. `launchGoalLead` builds a goal lead's launcher, with `goalLeadSettings`, and `relaunch` gives it the same resume-or-fresh fallback as `crew followup`. `retireGoal` ends a goal for `crew goal done` and `abandon`.
- **The lead (`cmd_lead.go`):** `crew lead` starts a lead in `lead/` with its project (`CREW_PROJECT`) and `CREW_LEAD_FINGERPRINT` in its environment. `leadFingerprint` is the fingerprint of the lead's flags (`leadFlags`: its permission mode and `--settings`, for its project), `lead/.claude/settings.json` and the lead's agent files, the same rule as a launcher's. The hook finds the project in `CREW_PROJECT`, as `crew lead` set it. `crew lead --hook` (`leadHook`) compares it with the session's and prints one line when they differ. Then it prints the session's news (`leadNews`), for every lead, the phone lead included, and nothing at all for a worker or goal lead.
- **News (`news.go`):** what the leads hear (see [What the lead hears](#what-the-lead-hears)). `recordNews` appends a line to the day's file; `tickNews` is one tick's, which prints each line as tick always has and keeps it; `leadNews` reads a session's record (`readSessionNews`), picks what it hasn't heard, and `newsMessage` fits it into the room the hook has left. `pruneNews`, at the end of a tick, removes what's older than `newsKept`.
- **Worktrees (`worktree.go`):** `worktreeCreate` and `worktreeRemove` are the only places task worktrees are made or removed, for both `WORKTREE_TOOL` values. `setupWorktree` wraps `worktreeCreate` for a task: it creates the worktree unless it exists (on the task's local branch, or a new one from `origin/<base>`), refuses one that a failed Worktrunk dispatch left behind (`crew cleanup <task> --force` clears it), and copies the `WORKTREE_COPY` files. Its callers run it without the ledger lock, since Worktrunk hooks can take minutes. A missing branch comes from `origin/<branch>` when another machine pushed it. `ensureWorktree` is how `crew followup` and `crew restack` find a task's worktree on this machine: it makes it at `$WORK_ROOT/<p>/<id>` if it's missing (on a machine the task moved to, say), rewrites `worktree:` when the recorded path differs, and logs "recreated worktree from origin/<branch>", or "started over: … was never pushed from <machine>" when the branch is nowhere and starts again from its base. `crew observe` and `crew cleanup` treat a missing worktree as nothing to do. With `worktrunk`, crew never passes `--yes`: hooks you haven't approved make `wt` fail non-interactively, and dispatch stops before a worker starts. It checks that the JSON `path` `wt` returns is the expected one. If a hook fails after `wt` has made the worktree, the task never records it, and the next dispatch refuses that leftover directory instead of starting a worker in a half-set-up worktree.
- **Services (`services_linux.go`, `services_darwin.go`):** the only places crew runs `systemctl` or `launchctl`. Each file defines the same functions, and build tags pick one, so callers never ask which system they're on. `crewServices` names the units or jobs; `enableServices` and `disableServices` turn them on and off now (`crew host up`, `crew host down`, the stand-down), `serviceEnabled` and `servicePath` are what `crew install` and `crew doctor` read, `restartLeadService` is `crew upgrade`'s restart, and `installServices` is `crew install`'s step (manifest component `systemd`, or `launchd`). What they share, so it's tested on Linux, is in `services.go`: `renderUnit`, `renderPlist` and `readPlist`, a reader for the plists crew ships.
  - On a Mac, turning a job on is `launchctl enable gui/<uid>/<label>`, then `bootstrap` (a job already loaded counts as done, and it's retried for a few seconds, since launchd can refuse it just after a bootout); off is `disable`, so it stays off after a login, then `bootout`. "Enabled" means loaded: `launchctl print` succeeds. A changed plist of a loaded job is booted out and bootstrapped again: launchd never rereads one. `restartLeadService` is `launchctl kickstart -k`.
  - Booting out a job can end crew itself, when crew runs in that job: the tick's stand-down runs in `crew-tick`, and a phone lead's `crew upgrade` in `crew-lead`. So for each job the bootout is the last thing crew asks of launchd. `crewServices` lists `crew-tick` last, and the stand-down turns the services off as its last step. A reload's bootout and bootstrap run in a shell in a session of its own, which loads the job again even if crew has ended.
- **This machine (`machine_linux.go`, `machine_darwin.go`):** `machineName` is its name for the lease, and `installTools` how `crew install` suggests getting the tools it lacks (pacman, or Homebrew).
- **Processes (`proc.go`):** `stopProcessesIn` ends the processes left in a worktree or checkout, for `crew cleanup` and `crew goal done`. `processesToStop` chooses them, the same way on both systems: those whose working directory is in it, without a terminal, other than crew and the processes that started it. `processes` lists them per system: from `/proc` on Linux (`proc_linux.go`), and on a Mac (`proc_darwin.go`) from `/bin/ps -A -o pid=,ppid=,tty=,stat=` and `/usr/sbin/lsof -nP -a -d cwd -F pn`, named by their full paths since a launchd job's `PATH` may lack `/usr/sbin`. The parsing of all three is in `proc.go`, so it's tested on Linux; the `ps` and `lsof` samples in `proc_test.go` are written from their man pages. When the processes can't be listed, it warns and leaves them running.
- **Commands:** one `cmd…` function each, listed in `commands` in `main.go`. `version` and `guard` run before the home is read: the launcher checks a download with `version`, and the guard must work whatever the home's settings say.

## The write guard (`crew guard`)

It's called from the agents' frontmatter hooks, and from the hooks in `lead/.claude/settings.json` and `config/worker-settings.json`, as `"${CREW_HOME:-$HOME/crew}/bin/crew-guard" <role>` on Edit, Write and NotebookEdit. `bin/crew-guard` is a two-line `sh` file that runs `crew guard <role>`: it stays, so sessions started before an upgrade keep their hook (a hook command that's gone would count as a non-blocking error, and allow their edits). The guard reads the hook JSON on stdin (`.cwd`, `.tool_input.file_path`). Exit 0 allows the call; exit 2 blocks it, and stderr goes back to the agent. It blocks whenever it can't work out where a path leads: input that isn't JSON, a symlink loop. Paths are judged by where they lead, symlinks resolved (`canonical`, which works like `realpath -m`).

- In the crew home, only the state paths, `projects/` and `reports/`, take edits, for every role. The rest of the home (`bin/`, `agents/`, `config/`, `templates/`, `lead/`, `.claude/`, `.git/`, the root files) is crew itself, and is blocked.
- Always allowed elsewhere: `/tmp`/`$TMPDIR`, `~/.claude/jobs`, `~/.claude/plans`, `$CLAUDE_JOB_DIR`.
- `worker`: only paths inside the git toplevel of `$CLAUDE_PROJECT_DIR` (falling back to `cwd`), and never when that toplevel is the main checkout.
- `lead` (the lead and goal leads), `gardener`: nothing else.
- A project's `memory.md` takes edits only from the `lead` role: `worker` and `gardener` are told to suggest the fact with `crew remember` instead. It's a tripwire, like the rest of the guard: a goal lead shares the lead's role, so only its prompt keeps it out, and a Bash write isn't checked.
- A project's `mcp.json` and `mcp.local.json` take edits from no role. Every lead starts their servers without asking, so they're the user's to change by hand. A goal lead shares the lead's role, which is why the lead is blocked too.

The target path is structured input, so this needs no shell parsing. Bash commands aren't checked: shell parsing can never be complete.

On a Mac's usual case-insensitive APFS volume, `~/Crew/projects/…` is the home `~/crew`'s ledger, but the guard compares paths as spelled, so it blocks that edit. That errs only one way: it never allows an edit it should block. Paths aren't lowercased to "fix" it, since a case-sensitive volume would then be judged wrongly. The one exception errs the same way: a project's `memory.md`, `mcp.json` and `mcp.local.json` are matched ignoring case, so `Memory.md` is blocked too, on any volume.

Why the hook is in two places:

- The lead and the implementer have no `tools:` allowlist, only `disallowedTools`. A `tools:` list can name MCP servers only one by one, so a shared allowlist would hide every repo's servers or leak one repo's into all of them. Without it, each session gets the MCP servers configured for its repo, and those its project declares in `mcp.json`.
- They can also spawn any subagent, apart from the crew's own agents (`Agent(lead)`, `Agent(implementer)`, `Agent(gardener)`, `Agent(misses)` and `Agent(goal-lead)` are denied in their settings) and the Claude Code agent types no role uses (`Agent(claude)`, `Agent(Plan)`, `Agent(statusline-setup)`).
- A frontmatter hook runs only while its own agent runs, so it doesn't guard a `general-purpose` subagent's edits. The settings hook does: settings hooks fire for subagent tool calls too.
- The frontmatter copy stays for a session started without its settings file, or with an edited one that dropped the hook (`crew doctor` flags that).

## Bash: no sandbox

No crew session runs in Claude Code's sandbox. It was tried and dropped:

- On Linux it gives sandboxed commands their own network namespace, so they can't reach `localhost:<port>`. Test suites that need a local database or cache (a Rails app's `bin/rspec`, for example) failed.
- Exempting those commands with `excludedCommands` depended on how the agent phrased them (a pipe or `cd … &&` missed the rule), and an exempt test runner executes code the worker wrote anyway, so little protection was left.
- Wrapping the whole worker in our own bubblewrap doesn't work either: `claude --bg` hands the session to the `claude daemon` process, so it isn't a child of the command `crew` runs.

What governs Bash instead:

- **Workers** run in `WORKER_PERMISSION_MODE` (`auto` by default): Claude Code's classifier approves routine commands and stops risky ones, as in your own sessions. The `allow` rules in `worker-settings.json` skip the classifier for the usual git and gh commands; the `deny` rules catch `gh pr merge` and force pushes. The implementer prompt tells workers to keep shell writes to their worktree, the ledger, temp directories and tool caches.
- **The gardener and `crew observe`** run with `--permission-prompts none` and a read-only `allow` list, so any other command is denied: `crew observe` with `readonly-settings.json`, and the gardener and the misses agent with `gardener-settings.json`, the same list plus `crew remember`.
- **`crew review-eval`'s reviewer** runs in `auto` mode with `readonly-settings.json` and `--permission-prompts none`: the classifier decides what the list doesn't cover, as it does for the reviewer under a worker, and anything that would prompt is denied. Its judge has no tools (`--tools ""`).
- **The lead** runs in `LEAD_PERMISSION_MODE` (`auto` by default) in the home's `lead/`, and **goal leads** in the same mode in their own checkouts. `crew guard` keeps their file edits to the ledger.
- **An allow rule's `*` goes after the subcommand**, never before it. `Bash(git -C * show *)` would also approve `git -C . -c core.pager=<program> show`, and Claude Code warns about such a rule at every start. `tests/guard.sh` checks the settings files for it.
- **Network is left open.** `WebFetch(domain:*)` pre-allows every host, so background sessions never stop at a network prompt.

## `crew install`

Order: check dependencies and the Claude Code version (≥ 2.1.293) → agents → `env.CREW_HOME`, `WORK_ROOT` and the lead's `settings.local.json` → links → fish completions → services (systemd, or launchd) → manifest → the optional AGENTS.md setting → next steps. It only puts files where Claude Code, your `PATH`, fish and systemd or launchd look for them, and writes the lead's gitignored `lead/.claude/settings.local.json` for this machine; it changes nothing tracked in the home.

- **The home** is `CREW_HOME`, else the checkout of the `bin/crew` that ran (symlinks resolved), so `~/crew/bin/crew install` works straight after a clone.
- **What gets installed** is discovered, not listed: every `agents/*.md`, every file under `fish/` (the completions), and every `systemd/*` (or on a Mac every `launchd/*.plist`). Adding a file here is enough to ship it. The links, `crew` and `lead`, are the exception: `crew-guard` in the same `bin/` is for hooks, not for `PATH`.
- **Links** (`link`, component `links`): `~/.local/bin/crew` and `~/.local/bin/lead` point at the home's `bin/crew` and `bin/lead`, and the launcher finds its home through them, so nothing needs `CREW_HOME` in a shell. A link that points there already is left alone. Anything else at that path, a file or a link to another home, is backed up and replaced by rename. When `~/.local/bin` isn't on the `PATH` install runs with, it says what to add; it never edits a shell's config. `crew doctor` checks the links as a required check, and `~/.local/bin` on its `PATH` as an optional one, since that may not be your shell's.
- **Files are replaced by rename** (`installContent`: a temp file in the same directory, then a rename), never rewritten in place, so a running guard hook never reads a half-written file. A file that differs is backed up first.
- **A home other than `~/crew`** needs nothing in the links, which name the home itself. It's substituted into the systemd services (`renderUnit`) *before* comparing, so an unchanged re-run takes no backups. On a Mac every plist is rendered (`renderPlist`): launchd expands nothing, so `%h/crew` becomes the home and every other `%h` the user's home, XML-escaped. It also makes the home's `logs/`, which launchd needs before it starts a job.
- **`~/.claude/settings.json`** is rewritten, after a backup, only when a value crew sets there changes. It keeps its keys in their order (`json.go`).
- **Stale files** (`prune`): `~/.local/share/agent-crew/manifest` records `component<TAB>path` for every shipped file. After installing a component (`agents`, `links`, `fish`, `systemd` or `launchd`), files the previous install of that component shipped and this one doesn't are backed up and removed (services are turned off first). A symlink is backed up as a link, never as the file it points at. This is how the fish `lead` function and `conf.d` snippet that installs before 0.14 shipped are removed. Components skipped with `--no-fish`/`--no-services` keep their manifest entries and lose nothing, and only paths under the component's current root are touched.
- **The AGENTS.md question** is asked only if the setting is off and the user hasn't declined before (`~/.local/share/agent-crew/agents-md-declined`).
- **Re-running** is idempotent: a second run with no changes in the home backs nothing up. Backups go to `~/.local/share/agent-crew/backups/<timestamp>/`.
- **Services** are installed but not enabled: `crew host up` enables them. Install names the ones that are off on this machine. On a Mac, a plist installed in `~/Library/LaunchAgents/` would load at the next login, so the shipped ones say `Disabled`; `launchctl enable` overrides that.

Flags: `--yes`, `--no-fish`, `--no-services` (the systemd units, or the launchd jobs), `--skip-agents-md-setting`.

## Verification

```bash
tests/run.sh            # lint + guard + crew-e2e + host; must pass before a change is done
```

- **`lint`**: `gofmt`, `go vet` for Linux and for macOS, `go test ./...` (the ledger model, settings files, the guard's table, `resolve`, statuses against `LEDGER.md`, each launchd job against its unit, plist rendering and reading, `/proc`, `ps` and `lsof` output, and `crew codex` stopping a stalled Codex), `sh -n` on `bin/`, `bash -n` on the tests, shellcheck on both, fish syntax, JSON validity, and `claude plugin validate agents`.
- **`guard`**: the write-guard allow/block table, run directly and through the lead and worker settings hooks, the home's state paths among them, plus checks that this repo tracks no state, that the lead, the implementer and the goal lead have no tool allowlist, that no settings file turns the sandbox on, that the lead and workers default to auto mode, that the settings run `crew commit --hook` and load project memory, that the lead service leaves itself stopped on exit 3, and that the agents' prompts agree with `crew` and the settings.
- **`crew-e2e`**: `crew` end to end in a crew home made from this checkout (`make_home`, which puts a binary built from this checkout in its `bin/release/`), against a bare-repo remote, with stub `claude`, `gh`, `wt` and `codex`.
- **`host`**: a machine and its home, in fake `HOME`s: `crew install` (a fresh install and its links, unchanged re-runs, edited, new and dropped files, a stray file where a link goes, skipped components, the AGENTS.md question, a home outside `~/crew`, `crew doctor`'s checks), the lease between two machines (`host up`, `--take`, a lost lease, the stand-down, `host down`, `crew serve`, `lead` run through its link), `crew setup`, `crew upgrade` to a release tag in a fake public repo (its confirmation, the pause it makes and lifts, the migration it runs, a conflict), and the launcher (a download, a failed one, `CREW_VERSION`), with `tests/stubs/curl` serving the releases.

Every suite runs in a fake `HOME` under `tests/.tmp/` with the stubs first on `PATH`, so the tests never start a model session or touch the real setup. The stubs include a `crew` that refuses every call, behind the `bin/` of the home a suite makes, so no `crew` but that home's can run; `make_home` refuses a copy of the repo that isn't a git checkout, and `isolate_home` clears every `CREW_` setting the caller had. The shell suites run only on Linux: they use GNU and util-linux tools, and `/proc`. On macOS, `go test ./...` runs in the release workflow, and the rest is the live checks M1–M8 below. See `tests/README.md` for how to add cases.

What the tests *can't* cover is the live Claude Code behaviour listed below. After changing anything that depends on it, do a smoke test with a tiny task.

- **Agent view / background sessions** (`--bg`, `claude agents --json`, `claude rm`) are a research preview. Their output formats are the most fragile contracts.
- **Resuming a background session:** `claude --resume <session> --bg` with launch flags (`--agent`, `--settings`, …) starts a copy under a new session, whether or not the session's process is still open. 2.1.284 says so in a `note:` line ("keeps its own saved options, so the flags you passed started a copy… Without flags, the same command continues <session> itself") and prints the job ID in color. `crew followup` resumes with no flags and relies on the session keeping its agent, permission mode, auto-compact window, settings and `--add-dir`. A finished session also keeps its process open for about an hour (state `done`, `pid` set), and resuming it then starts a copy too ("session <id> is already running in the background"), so `crew followup` runs `claude stop` on it first. A live run confirmed both causes of a copy. On 2.1.328 a live run confirmed that a resume after `claude stop` continues the session in place, and timed it. For about 3 seconds `claude agents` lists the old entry (`done`, `pid` null). Then the new process shows `working` with a `pid` and no `status`, then `idle`, then `busy`. Its transcript still ends with the last turn until about half a second after the process shows, when the prompt is written. In that half second the session reads as idle, and a second `crew goal note` stopped it or resumed it into a copy. The resume touches the transcript and appends metadata before the prompt (seen in the 2.1.328 code), so a changed transcript isn't enough: `waitForLaunch` waits for a prompt or a reply past where the transcript ended before the launch, and `launchSession` sends nothing to a session whose process stays open.
- **Removing a background session:** the agent-view docs say `claude rm` removes a session from the list, and leaves "a worktree you created yourself and started the session inside". They don't say whether it ends a process that's still open, so `crew cleanup` runs `claude stop` first. That `claude rm` needs no confirmation when run without a terminal hasn't been confirmed by a live run.
- **Confirming a launch:** `crew` counts a launch as started once `claude agents` lists the job with a `pid` and a `sessionId` that starts with the job ID, and the session's transcript has a prompt or a reply past where it ended before the launch, or it has none: a resumed process takes its prompt a moment after it shows ("Resuming a background session"). On 2.1.296 every job's ID was its session's first 8 characters. A resumed job's `pid` and `sessionId` come from its live process. A process that has just started can show a new session ID before it loads the resumed one. A resume of a missing session ends in `failed` about 10 seconds after launch ("source session … not found"). This comes from one incident and from reading the 2.1.296 code; a live run hasn't confirmed the timing.
- **A resumed background session keeps its model and effort.** crew passes `--model` and `--effort` only on a fresh start (`launchSession`), and starts a worker fresh when its task's model or effort changed, so a resume relies on the session keeping what it started with, like its other launch options. Not confirmed by a live run. - **Stacked PRs on GitHub:** when a merged PR's head branch is deleted, GitHub retargets the open PRs based on it to the branch it merged into; deleting an unmerged branch closes them instead. - **A PR's mergeability on GitHub:** `gh pr view --json mergeable` is `CONFLICTING` against the base branch as it is now, and `UNKNOWN` while GitHub works it out. `baseRefOid` isn't the base as it is now: on 2026-11-15 an open PR whose head was pushed after `main` moved still gave an older `main`. So `crew catch-up` reads the base's commit from origin.
- **Whether GitHub would merge a PR now:** `crew status` reads `gh pr view --json reviewDecision,mergeStateStatus`. It takes `reviewDecision` `CHANGES_REQUESTED` and `REVIEW_REQUIRED` to stand in the way, and `mergeStateStatus` `BEHIND` only when the branch rules want the branch up to date with its base, and `BLOCKED` for any branch rule still unmet, a required check that hasn't reported included. Check: on a repo whose branch rules need a review and an up-to-date branch, open a PR and run `gh pr view <url> --json reviewDecision,mergeStateStatus` before and after approving it and after its base moves.
